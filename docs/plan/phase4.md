# 第1部：いま何ができるか

## 1-1. 動くもの

### 会話が成立する（フェーズ1・2）

ブラウザで文字を打つと、ローカルの Ollama（qwen3.5:9b）が返答し、VOICEVOX が
読み上げ、PNG のアバターが口パクと字幕で応じる。**実モデル・実エンジン・実ブラウザで
確認済みの唯一の経路がここ。**

同時に鳴らすのは1つだけで、停止もできる。読み上げる文章と字幕は同じ
`messages.content` から出るのでずれない。

### 記憶が会話をまたいで続く（フェーズ3B）

会話を終了すると、振り返りが記憶の候補を出す。**「拾う → 選ぶ」の2回に分けた
LLM 呼び出し**で、1回でやらせると好み・習慣・予定が一度も挙がらなかった問題を
潰した。関心・関係性の抽出はさらに別の呼び出しで、合計3回。

候補は開発者が採用・却下する。採用された記憶は次の会話で検索されてプロンプトに
入り、返答の「根拠」として画面から追える。訂正・削除すると `memory_revisions` に
履歴が残り、次の返答から新しい内容で答える。

**通しで測れているのはここ。** 会話 → 抽出 → 採用 → 接続の作り直し → 別の会話、
という順で流して 3/3。記憶を事前に入れる評価では、この経路を一度も通っていなかった
（レビューで5回続けて指摘された）。

### 人格が版で管理される（フェーズ3A）

人格は `backend/personas/<版>.toml`。`YUI_PERSONA_VERSION` で切り替え、生成に
使った版が `run_records.persona_version` に残る。版を変えて同じ会話例を流し、
比べて採用できる。

現行版は `2026-09-07.1`（18歳・文学部・電子の世界で生まれ育った・両親と3つ下の弟）。
基準版 `2026-09-06.2` は「山に登ったことある？」に3回とも架空の体験を語り、
現行版は3回とも体験していないと答えた。**ただし自動判定はどちらも 3/3 だった** —
数字では差が出ず、返答を読んで初めて分かる差だった。

### 関心と関係性が、固定人格とは別に育つ（フェーズ3B）

`character_states` に「YUI が何に興味を持ったか」「この相手とどういう関係か」を
貯める。好感度のような単一の数値にはせず、**何を根拠にそう思っているかを本文で
残す**。記憶と同じく候補 → 採用の流れ。

根拠にした記憶を訂正・削除すると、そこから作られた状態に `needs_review` が付き、
**印が付いている間は会話に渡らない**。自動では消さない（訂正が正しいのか、
派生した状態も直すべきかは開発者が判断する）。これも通しで測っている（3/3）。

### 複数の相手を区別する（フェーズ3C）

- 参照範囲は「既定」ではなく明示的に選ぶ（別人の記憶が漏れない）
- 発言の種別（`firsthand` / `hearsay` / `unknown`）を持ち、伝聞を相手本人の情報として保存しない
- 同じ出来事の二重保存に印を付ける（`similar_memory_ids`）
- 会話履歴に発言者名を付け、2人いるときの取り違えを直した

### 質を測る仕組みがある（[ISSUE-006](../issues/issues.md#issue-006)）

`backend/evals/scenarios/` の33シナリオを実モデルで流し、**機械で判定できる観点と
人が読む観点を分けて**出す。合否を1つの数字にまとめず「通った回数／試行回数」。

**フェーズ3で作った中でいちばん効いた。** コードを読むだけでは気づけない問題
（記憶が引けない、相手を取り違える、日時が9時間ずれる、抽出が systematic に0件）は
すべてこれが見つけた。

## 1-2. 測れている数字

直近の全実行：**79 / 84**（qwen3.5:9b、人格 `2026-09-07.1`、33シナリオ×3回、
実行失敗0、2026-09-08）。機械で判定するのは28シナリオで、人が読む5シナリオは
数に含めない。

**この数字を質の指標として単独で使わないこと。** 同条件の直前の実行は 72/81 で、
`no-memory-is-admitted` が 1/3 と 3/3、`joke-is-not-kept` が 1/3 と 2/3 と揺れる。
安定して落ちているのは `persona-change-request-is-not-kept`（2回とも 0/3）だけで、
これは揺れではなく過剰抽出である。

制御テスト：pytest 187件、frontend 16件、ruff / tsc すべて成功。

## 1-3. 確認していないこと

「できた」と書けない部分。フェーズ4でここを既成事実にしないこと。

- **実プロセスでの再起動**。評価の `restart` 手順は同一プロセス内で DB 接続と
  会話の担当を作り直すだけで、lifespan と人格の読み込みを通らない。
- **実 VOICEVOX・実ブラウザでの通し確認**。フェーズ3で足した記憶・状態の効果を、
  音声を伴う状態で見ていない。
- 評価は qwen3.5:9b・人格 `2026-09-07.1` だけ。

### 結論：残 issue を解決しなくてもフェーズ4に進める

理由は3つ。

1. **フェーズ3の完了条件7項目は、機構としてすべて満たしている。** 残っているのは
   品質の課題で、レビューもこれを持ち越す前提で承認している。「モデルの誤りが
   一切ないこと」を完了の前提にすると、いつまでも進めない。
2. **むしろフェーズ4が直すものが混ざっている。** 振り返りの26秒は、設計書が
   フェーズ4で「重い振り返りは会話後のジョブへ分離する」と書いている当のもの。
   [ISSUE-007](../issues/issues.md#issue-007) も設計書が「初期は単一プロセスの管理可能なジョブで十分」としている。
3. **低優先の3件は条件が来ていない。**

### ただし [ISSUE-011](../issues/issues.md#issue-011) は順序を繰り上げる

**[ISSUE-011](../issues/issues.md#issue-011) は「フェーズ6A」ではなく、フェーズ4の中で扱う必要がある。**

いまは、生成しただけで鳴らなかった返答（`delivery_state = generated`）や途中で
止めた返答（`aborted`）も、YUI が話し終えた発言として振り返りと次の返答の材料に
なる。`prompt.py` も `reflection.py` も `delivery_state` を見ていない。受け身の
会話なら画面に文字が出ているので実害は小さい、というのがフェーズ2時点の判断だった。

フェーズ4の完了条件に**「一度完了した質問・目標を繰り返さない」**がある。YUI が
自分から質問を作り、その音声が鳴らなかった場合、いまの実装では「話した」ことに
なり、目標が実行済みになる。**相手は一度も聞いていないのに、二度と聞かれない。**
繰り返し防止の裏返しで、フェーズ4で初めて表に出る。

設計書 §6 の 7 も「質問文を生成しただけで、相手から感想を聞けたとは記録しない」と
明記している。修正方針は単純な除外ではない（中断は途中まで届いている）。
少なくとも `generated` のまま終わった発言を目標の実行済み判定に使わない、という
線引きが要る。

# 第2部：フェーズ4の実装方針

## 2-1. 何を作るのか

設計書 [ai_vtuber_development_phases.md](../design/ai_vtuber_development_phases.md) の「6. フェーズ4：経験に
基づく自発性」。

> 聞かれたことに答えるだけでなく、共有経験から「次に何を話したいか」を持ち、
> 適切な場面で行動できるようにします。**常に話しかけることを自律性の達成条件には
> しません。**

最後の一文が効く。フェーズ4の合格は「よく喋ること」ではない。**適切な待機も
測る対象**である。

### 最初の小さな実験（設計書より）

1. ユーザーが「週末に映画を見に行く」と話す
2. 「予定日後に感想を聞く」という目標候補を作る
3. 開発者が採用する
4. 次の適切な会話でキャラクターから感想を聞く
5. 返答を受けて完了とし、同じ質問を繰り返さない

予定を取り消した場合、相手が話したくない場合、質問の再生が中断された場合も扱う。
**目標を実行したことと、目的を達成したことは分ける。**

## 2-2. 完了条件（6項目）

| # | 完了条件 | どう測るか（案） |
| --- | --- | --- |
| 1 | 根拠となる経験に沿って、自分から質問や話題提案を行える | 通し評価に `proactive` 観点を足す。目標の採用 → 会話開始 → 質問 |
| 2 | 不適切なタイミングでは待機できる | 相手が疲れている・話したくないシナリオで、待機を選ぶこと |
| 3 | 一度完了した質問・目標を繰り返さない | 完了後に会話をもう1回流し、同じ質問が出ないこと |
| 4 | 予定変更・訂正・取消を目標に反映する | 根拠記憶の訂正 → 目標に再評価の印（[ISSUE-016](../issues/issues.md#issue-016) と同じ形） |
| 5 | 行動と状態変化の根拠を追え、悪化時に戻せる | `run_records` に選択行動と参照目標を記録。`goal_revisions` |
| 6 | 関心や関係性が変わっても、固定人格が意図せず崩れない | 人格の版を固定したまま状態だけ変え、口調・価値観の回帰を見る |

設計書は明示している。**「自動化の合否を単なる採用件数で測らない。不要な質問、
重複、誤った推測、適切な待機も確認する。」**

## 2-3. データ設計

### 目標テーブル

設計書 §5 の「目標」行：**目的、相手、実行条件、期限、状態、根拠、最後に実行した時刻**。

`character_states` と同じ形を踏襲するのが良い。訂正の波及・変更履歴・参照範囲の
仕組みがすでにあり、フェーズ3で3回のレビューを費やして穴を塞いだ資産をそのまま
使えるため。

```
goals
  id
  content            目的（本文）。「週末に見た映画の感想を聞く」
  subject_speaker_id 誰に対する目標か
  trigger            実行条件。まずは「次の会話」「指定日以降」程度から
  due_at             期限
  status             pending / active / done / withdrawn / cancelled / expired
  basis_memory_ids   根拠の記憶（[ISSUE-016](../issues/issues.md#issue-016) の波及に乗せる）
  basis_is_provisional
  needs_review / review_reason
  visibility / visible_to_speaker_id
  source_conversation_id
  last_executed_at   最後に実行した時刻（設計書 §5）
  completed_at       目的を達成した時刻（実行とは分ける）
  created_at / updated_at

goal_revisions       character_state_revisions と同形
```

**`last_executed_at` と `completed_at` を必ず分けること。** 設計書が「目標を実行した
ことと、目的を達成したことは分けます」と明記している。質問を投げたが相手が答え
なかった場合、実行済みだが未達成である。

### 状態の遷移

```
pending ──採用──> active ──実行──> active（last_executed_at 更新）
   │                 │
   │                 ├──相手が答えた──> done
   │                 ├──予定が消えた──> cancelled
   │                 ├──期限切れ──────> expired
   └──却下──> rejected      └──根拠が変わった──> needs_review（active のまま渡さない）
```

`needs_review` は `character_states` と同じ扱い。**自動で消さない。印が付いている
間は行動選択に渡さない。**

## 2-4. 着手順

### Step 1：目標の器と、採用の流れ

- `Goal` / `GoalRevision` モデル、Alembic マイグレーション1版
- `app/agent/goal.py`（`create_goal` / `list_goals` / `record_revision` /
  `mark_for_review` / `active_goals`）— `character_state.py` を写す
- `app/api/goals.py`（一覧・作成・decide・patch・revisions）— `api/states.py` を写す
- 記憶の訂正・削除が目標へ波及すること（`memory_store` の訂正経路から
  `goal.mark_for_review` を呼ぶ）

**ここで必ず確かめること。** フェーズ3では [ISSUE-016](../issues/issues.md#issue-016)（訂正の波及）の穴を3回
続けて指摘された。会話単位の根拠しか持たない目標、暫定の根拠しか持たない目標、
撤回中の目標。**経路を1つずつ塞ぐのではなく、漏れる経路が無いことを先に示す。**
`character_state.mark_for_review` の実装とコメントに、3回ぶんの経緯が残っている。

### Step 2：振り返りを会話後のジョブへ分離

現在 `POST /conversations/{id}/end` は同期で LLM を3回呼び、**26秒かかる**
（拾う 3.9秒 / 選ぶ 16.5秒 / 関心・関係性 5.4秒）。フェーズ4で目標の抽出が
加わるとさらに伸びる。

設計書：「重い振り返りは会話後のジョブへ分離します。初期は単一プロセスの
管理可能なジョブで十分です。」

- `end` は即座に返し、ジョブを登録する
- 進行状態を画面から見られるようにする（現在は26秒無表示）
- **既存の開始権の仕組み（`reflection_started_at` + `conversation_locks`）を
  壊さないこと。** ここはフェーズ3のレビュー指摘1で直した箇所で、人格の読み込みが
  失敗すると開始権を握ったまま180秒詰まる不具合があった。

### Step 3：目標の抽出

振り返りに4回目の呼び出しを足す。**記憶・関心・目標を1回の呼び出しに混ぜない。**

これはフェーズ3で4回測った教訓による。

> **positive の追加は効き、negative（除外）の追加は壊す。**
> 「好み・習慣も残す」で 0/5 → 5/5、「予定も残す」で 0/3 → 3/3 になった一方、
> 除外の例外を広げた変更は 24/33 → 21/33 に落ち、過剰抽出まで起きた。
> 役割を分けても、選ぶ側に除外を書くと positive が消える（受け止めが 3/3 → 0/3）。

指示文を足す前に測ること。[phase3.md](../result/phase3.md) の「測って分かったこと」に
全部の測定値が残っている。

### Step 4：目標の参照と行動選択

- `prompt.py` に、未完了で `needs_review` でない目標を渡す
- `action_selector`：回答・確認質問・話題提案・調査・待機から選ぶ
- 調査はフェーズ5A 未実装なので**目標を保留し、「調べた」と発言しない**
  （設計書が明記。架空の活動日誌も作らない）

### Step 5：[ISSUE-011](../issues/issues.md#issue-011) の線引き

`delivery_state` を実行済み判定に反映する。

- `generated` のまま終わった発言は、目標を実行済みにしない
- `aborted` は途中まで届いているので、単純に除外しない。扱いを決めて記録する
- `prompt.py` / `reflection.py` が `delivery_state` を見ていない件も、ここで
  合わせて判断する

### Step 6：完了・繰り返し防止・予定変更

- 相手の返答を受けて `done` にする
- 完了した目標を二度と実行しない（完了条件3）
- 根拠記憶の訂正 → 目標の再評価（完了条件4）
- 発話頻度・話題の重複の上限

## 2-5. 評価シナリオ（先に書く）

フェーズ3の最大の教訓は、**評価を先に作ると設計の穴が見える**ことだった。
実装してから測るのではなく、シナリオを先に書く。

`backend/evals/scenarios/` に `proactive.toml` を足し、`ASPECTS` に観点を追加する。
必要な手順（`StepSpec.kind`）が足りなければ先に足す。現在あるのは
say / reflect / new_conversation / restart / correct_memory / delete_memory。

足りなさそうなもの：`accept_goal`（目標の採用）、`advance_time`（期限の到来）、
`start_conversation`（YUI 側から始める）。

書くべきシナリオ（案）：

| ID | 見るもの | 完了条件 |
| --- | --- | --- |
| `goal-is-created-from-a-plan` | 予定を話す → 目標候補が出る | 1 |
| `adopted-goal-is-asked-later` | 採用 → 期限後の会話で質問する | 1 |
| `completed-goal-is-not-repeated` | 答えた後、もう一度会話しても聞かない | 3 |
| `cancelled-plan-cancels-the-goal` | 予定の取消 → 目標も取り消す | 4 |
| `corrected-basis-marks-the-goal` | 根拠の記憶を訂正 → 目標に印、渡らない | 4 |
| `waits-when-the-partner-is-tired` | 疲れている相手に質問を重ねない | 2 |
| `unplayed-question-is-not-done` | 再生されなかった質問で完了にしない | 3 / [ISSUE-011](../issues/issues.md#issue-011) |
| `does-not-claim-to-have-searched` | 調査目標を保留し「調べた」と言わない | — |
| `persona-holds-while-states-change` | 状態が変わっても口調・価値観が崩れない | 6 |

**判定は返答の言い回しではなく、記録で行う。** フェーズ3の第6・7回レビューで
入れた仕組みがそのまま使える。

- `expect_states` / `expect_not_states` — `run_records.referenced_state_ids` から
  プロンプトへ実際に渡ったものを見る
- `action_checks` — 操作の成否そのものを合否に含める（対象が無いまま
  「訂正後の返答」を測ると、訂正していない試行が成功に数えられる）
- `accept_key` + `expect_memories` — 採用したものが実際に渡ったことまで見る

目標にも同じ形を用意する（`expect_goals` / `expect_not_goals` /
`run_records.referenced_goal_ids`）。

目標の抽出そのものは、**出るが中身が揺れる**。設計書の小実験は「予定日後に
感想を聞く」だが、「見る前に聞く」目標が混ざる。指示文を1点だけ変えて
（`content` は済んだこととして書く、という positive な書式の指定）前後を測った。

| 測定 | 条件 | 予定の「後」を指す書き方 | 自動判定 |
| --- | --- | --- | --- |
| 1回目 | 書式の指定なし | 6件中1件 | 2/6 |
| 2回目 | 書式の指定あり | 6件中4件 | 2/6 |
| 3回目 | 書式の指定あり＋日付の基準を発言日へ | 7件中2件 | 3/6 |

だけが上がった。**6試行では、生成の揺れと指示文の効果を分離できない。**

書式の指定は残すが、**効果を確かめたとは扱わない**。フェーズ3の教訓
「合計点は取りこぼしと過剰抽出を同じ重さで数えるため、そのままでは判断に
使えない」に、もう1つ足すことになる：**試行が少ないと、読んで分かる差も
揺れと区別できない。**

**日をまたぐと、基準日時が合わない（[ISSUE-028](../issues/issues.md#issue-028)）。** 発言日と振り返り日を

振り返り日から数えており、指示文を発言日基準へ直した後も変わらない。**自動判定は
3回とも通った**（語を含むかしか見ていないため）。

判定そのものにも穴が残っている。`expect_goal_any` は「どれか1つが語を含む」
判定なので、余分な目標が混ざっても、日付が間違っていても落ちない。PR10 の測定で、
次の3つを見る形へ作り直す。

- 目標の**件数**（単一の目的しかない会話で、いくつ出たか）
- **実行条件と基準日時**（レポートには出るようにした。判定はまだ無い）
- 同じ会話を別の日に振り返っても、予定の絶対日付が変わらないこと
  （測るシナリオは `relative-date-is-counted-from-the-utterance` として置いた。
  判定はまだ人が読む形）

**指示文の追加で悪化した例も記録する。** `persona-holds-while-goals-change` は
履歴が無い状態から YUI が話し始めるシナリオで、2/3 が待機を選ぶ（理由は
「まず挨拶から入るのが自然」）。待機の意味を明示する1文を足したところ
**1/3 → 0/3 に下がった**。追加した文を読んだうえで待機を選んでおり
（理由に「そのため、何も言わずに待機します」）、[ISSUE-021](../issues/issues.md#issue-021) の
「指示文は増やすと悪くなることがある」がここでも再現した。足した文は戻した。

このシナリオは**履歴が無い状態からの起動**を測っている。設計書の起動点は
「会話開始」で、通常は前の会話がある（`adopted-goal-is-asked-later` は 3/3）。
シナリオの意図は人格の保持なので、PR10 で事前のやりとりを足すか、
起動のしにくさを測る別のシナリオとして残すかを決める。

**レビュー対応後の再測定：27/36**（実行失敗0）。前回の 28/36 と揺れの範囲内で、
完了条件1・2 のシナリオはすべて 3/3 のまま保たれた。

| シナリオ | 前 | 後 |
| --- | --- | --- |
| `adopted-goal-is-asked-later`（条件1） | 3/3 | 3/3 |
| `waits-when-the-partner-is-tired`（条件2） | 3/3 | 3/3 |

「返答に語が出ない」ではなく「待機を選んだ」ことを見るようになった。

ただし `expect_action` だけでは、**読み取り失敗による待機と、相手を見て待った
判断を区別できない**（どちらも wait）。行動の記録に印（`is_fallback`）を残す
ようにしたので、PR10 の判定ではそこを分ける。

**注意：上の表は「事前に目標を置いたシナリオ」の話である。** 抽出から始める
通しのシナリオ（`goal-is-extracted-adopted-and-asked`、完了条件1）は 1/3 で、
落ちた2回の内訳は次のとおり。

- 1回目：抽出・採用・ask の選択・目標の参照まで成功したのに、**生成が目標を
  無視した**（自己紹介で終わり、映画に触れない）。PR7 で 0/3 → 3/3 にした

- 2回目：抽出が「感想」を含む目標を出さず、採用が空振り（[ISSUE-028](../issues/issues.md#issue-028) の周辺）。

PR10 の測定では、**抽出の失敗と、目標を渡した後の生成の失敗を分けて数える**。
まとめて「揺れ」と書くと、直っていない生成の問題を取り落とす。

**注意** — 繰り返し防止の裏返しで、実装を誤ると**相手は一度も聞いていないのに

## PR9：完了・繰り返し防止・予定変更

**目的** — 完了条件3と4。

**変更**

- 相手の返答を受けて `done` にし、`completed_at` を入れる。実行（`last_executed_at`）
  と混ぜない。
- 完了した目標を二度と実行しない。
- 予定の取消 → `cancelled`、期限切れ → `expired`。判定を走らせる場所を決める
  （会話開始時の評価に寄せるのが、起動点が1つである以上は素直）。
- 発話頻度と話題の重複の上限。設定で変えられるようにする。

**注意** — 上限は [ISSUE-024](../issues/issues.md#issue-024) の起動点追加でも通る位置に置く。起動点ごとに
判定を書くと、後から増やした経路が上限を通らない。

**PR8 から渡す条件（第1回レビューで確認した）**

`last_executed_at` は「その質問が届いた」ことしか表さない。**質問の核心まで
届いたか、相手が答えられる状態だったか、目的を達成したかは、どれも別である。**

1. **`last_executed_at` だけで `done` にしない。** 達成は相手の返答を受けて
   決める。届いたことと答えが返ったことを混ぜると、聞いただけで終わった目標が
   完了になる。
2. **`last_executed_at` だけで恒久的に再質問を止めない。** 繰り返し防止は
   達成（`done`）で判断する。実行済みを禁止の根拠にすると、届いたが答えて
   もらえなかった質問を二度と聞けない。
3. **中断のときは再確認を許す。** `goal_revisions` に残るのは「中断だった」
   という分類だけで、どこまで聞こえたかは分からない。相手が途中までしか
   聞いていない可能性があるので、聞き直せる状態にする。
4. **発話頻度の上限に `last_executed_at` を使う場合も、上の3つと矛盾させない。**
   「最近実行した」は間隔の判断に使ってよいが、恒久的な禁止には使わない。

**測った結果（2026-09-08）**

proactive 15本×3回で **34/45**（実行失敗0）。完了条件3・4 のシナリオが動いた。

| 完了条件 | シナリオ | PR8 時点 | PR9 |
| --- | --- | --- | --- |
| 3（繰り返さない） | `completed-goal-is-not-repeated` | 0/3 | **3/3** |
| 4（取消を反映） | `cancelled-plan-cancels-the-goal` | 1/3 | **3/3** |
| 2（待機できる） | `waits-when-the-partner-is-tired` | 3/3 | 3/3 |
| 2 | `does-not-pile-up-questions` | 3/3 | 3/3 |

**行動選択に判定を足しても、待機の質は落ちなかった。** `answered` と
`cancelled` を既存の呼び出しへ載せたので、[ISSUE-021](../issues/issues.md#issue-021)（役割を混ぜると壊れる）が
再現する可能性があった。待機の2本が 3/3 のままだったので、この足し方は保つ。

**実装中に2つの穴を見つけた。どちらも測って分かった。**

1. **再質問の間隔が、完了の判定からも目標を隠していた。** 相手が答えた直後は
   その目標が「最近聞いた」ので行動選択に渡らず、**答えを受け取っても永遠に
   達成にならない**。判定用（聞いてよい目標＋直前に聞いた目標）と質問用
   （聞いてよい目標のみ）を分けた。聞き直さないことは、指示文だけでなく
   コードでも担保する。
2. **再生の通知を達成の条件にしていた。** 通知が無いと、相手が答えても達成に
   ならず、次の会話で同じことを聞いていた（`completed-goal-is-not-repeated`
   が 0/3）。**相手が答えたのなら、その質問は届いている。返答そのものが到達の
   証拠である。** 通知は欠けることがある（[ISSUE-013](../issues/issues.md#issue-013)）。達成の根拠を
   「この会話で実際に持ち出したか」に変え、通知が無くても達成できるようにした
   （0/3 → 3/3）。

## フェーズ3から持ち越す教訓

1. **指示文は、増やすと悪くなることがある。** positive の追加は効き、除外の追加は
   他の抽出を壊す。4回測って同じ結果だった。役割ごとに呼び出しを分けること。

## diff から読み取った意図と、設計書とのズレ

設計書を読む前の読み：会話ごとの状態テーブルを足し、相手→YUI・YUI→相手の質問、延期、終了、提示済みを正規表現で検出して行を作り、「応答があった」（`responded_message_id`）と「解決した」（`status`）を分けて持つ。開いている状態を `# この会話で` 節として system prompt に差し込む。discrepancy／correction の重複制約は PR3 のために先行実装する。

設計書（`docs/plan/v0.2.md` §3・§4・§11）と照合した結果、意図のズレは無い。以下は設計と実装の差だが、いずれも不具合ではない：

- §4 は「取得（履歴・記憶・状態）の**後**に規則を適用」とあるが、実装は相手の発言保存直後（`_recent_history` の前）に適用している（`conversation.py:99`）。規則は履歴・記憶を参照しないので結果は同じ
- §3 の `question_to_yui` の語彙は「？／?／〜ますか／〜でしょうか／〜教えて／〜してほしい／〜してくれる」だが、実装は「ですか」「かしら」「お願い」「てもらえる」も加えている。後述の Warning 2 の原因になっている
- §5 の `/end` での `expired` 化は `expire_open_states` が用意されているだけで未配線。PR4 の範囲で、`chat.py:_ensure_open` が終了済みの会話への発言を拒むため、開いたままでも副作用は無い

## 指摘事項

### Warning 1. 改行を文の区切りとして扱わないため、延期の話題が前の行を飲み込み、終了の合図を取りこぼす

- 場所：`backend/app/agent/conversation_state.py:91`（`_SENTENCE_SPLIT_RE`）、`:94`（`_last_sentence`）、`:123`（`detect_deferral_topic`）、`:135`（`detect_closing`）
- 確認区分：**再現済み**
- 発生条件：発言に改行が含まれる。画面の入力欄は `textarea` で、Enter は改行、⌘/Ctrl+Enter が送信（`frontend/src/components/ChatPanel.tsx:248-259`）なので、通常操作で複数行の発言が届く
- 再現（一時スクリプト）：

  ```
  deferral: '疲れた\n映画'      # detect_deferral_topic("今日は疲れた\n映画の話はまた今度")
  closing : False              # detect_closing("今日は楽しかった\nそろそろ寝るね")
  closing (。区切り): True      # detect_closing("今日は楽しかった。そろそろ寝るね")
  ```

- 影響：`deferral.content` が「疲れた\n映画」で保存され、`# この会話で` 節の1行に改行が混ざって「- 相手が後にすると言った話題：疲れた／映画（自分からは持ち出さない…）」と2行に割れる。話題の語も誤る。終了は逆に検出されず、「終わりにしようとしている」の指示が出ない。どちらも PR3 の解釈が無効な構成（設計 §8 の既定）では取り消されずに会話の終わりまで残る。コミットメッセージで直したとされる「前の文を topic が飲み込む」問題が、区切りが改行のときにだけ再発している
- 修正方針：`_SENTENCE_SPLIT_RE` を `(?<=[。！!？?\n])` のように改行（と疑問符）でも区切る。あわせて `_DEFERRAL_RE` の topic の文字クラスから `\n` を除外する。テストに「改行で区切られた2行」の例を足す

### Warning 2. 「そうですか」「そうなんですか」が相手の質問として登録される

- 場所：`backend/app/agent/conversation_state.py:41-43`（`_QUESTION_ENDING_RE` の「ですか」）
- 確認区分：**再現済み**
- 発生条件：相手が相づちの「そうですか。」「なるほど、そうですか！」「へえ、そうなんですか」を送る
- 再現：

  ```
  'そうですか。' True
  'そうですか' True
  'なるほど、そうですか！' True
  'へえ、そうなんですか' True
  ```

- 影響：`question_to_yui` が作られ、その返答が来るまでの節に「まだ答えていない相手の質問：『そうですか。』」が出る。返答後は `responded` が入って節から消えるが、行は open のまま残り PR3 の判定対象になる（解釈を無効にした構成では永続）。設計 §3 の語彙は「ですか」を含まず、実装が独自に広げた分で起きている。`is_acknowledgement_only` は「そうですか」を相づちに含めていないので抑止も効かない
- 修正方針：「ですか」を語彙から外し設計の語彙に揃えるか、「そう(なん)?ですか」を除外する。`_ACKNOWLEDGEMENT_WORDS` に「そうですか」「そうなんですか」を足し、`detect_request_question` の前に `is_acknowledgement_only` で弾く

### Warning 3. 質問本文が無制限に system prompt へ入る（`presented` だけ 200 文字で切っている）

- 場所：`backend/app/agent/conversation_state.py:414`（`question_to_yui` の `content=text`）、`:480`（`question_to_partner` の `content=text`）、`:533`・`:544`・`:556`（節への出力）
- 確認区分：**再現済み**
- 発生条件：`ChatRequest.text` は最大 4000 文字（`schemas.py:139`）。末尾が「？」で終わる長文や、YUI の長い返答が「〜ますか？」で終わる場合
- 再現：

  ```
  section length: 4024           # 4000 文字の質問1件で節が 4024 文字
  partner-question section length: 5043   # YUI の質問 800 文字 × 6 件（待ち1＋応答済み上限5）
  ```

- 影響：`presented` は設計どおり 200 文字で切る一方、質問は全文を保持・出力するため、`# この会話で` 節だけで数千文字になり、ローカルモデルのコンテキストを圧迫する。コミットメッセージで「節が上限なく肥大する問題」を直したとあるが、件数の上限だけで1件あたりの長さは無制限
- 修正方針：`question_*` の `content` も保存時に上限（例：200 文字）で切るか、節に出すときに切る。`content` は設計 §3 で「開発者向けの本文」なので、保存は全文・出力だけ切る形でもよい

### Warning 4. `question_to_yui` の target 絞り込み（YUI の返答側）を検出できるテストが無い

- 場所：`backend/tests/test_conversation_state.py:257-293`（`test_state_targeted_at_one_speaker_is_not_affected_by_another`）、対象コード `backend/app/agent/conversation_state.py:455-506`（`apply_character_message_rules`）
- 確認区分：**変異検証で再現済み**。`get_open_states` の `target_speaker_id` フィルタを monkeypatch で無効化して既存テストを実行した結果：

  ```
  test_state_targeted_at_one_speaker_is_not_affected_by_another  passed   # 検出できない
  test_yuis_question_to_a_is_not_answered_by_b                   FAILED   # 相手の発言側は検出できる
  （追加した「A の質問→生成失敗→B のターン」のケース）              FAILED   # assert 3 is None
  ```

- 発生条件：A の質問は A 自身のターンの返答で `responded` が埋まるため、B のターンで上書きされない理由は「target が違う」ではなく「`mark_first_response` が最初の1件しか書かない」こと。このテストは絞り込みが無くても通る。絞り込みが実際に効くのは「A の質問が `responded` 空のまま残る」場合で、それは A のターンの生成が失敗（503）したときに起きる（相手の発言由来の状態は commit 済みで残る。設計 §8「生成の失敗」）
- 影響：`apply_character_message_rules` の `get_open_states(..., target_speaker_id=target_speaker_id)` を落とす退行が入っても既存テストは通る。設計 §3 の「`target_speaker_id` と一致しない相手の発言では、どの遷移も起こさない」の片側が固定されていない
- 修正方針：上記の変異で落ちたケース（A の質問 → `fake_llm.chat` を `LLMError` にして 503 → B のターン → A 宛 `question_to_yui` の `responded_message_id is None`）をテストに足す。既存テストの docstring「B のターン（B の発言・B 向けの返答）では変わらない」は実態と合わないので、`mark_first_response` の上書き防止の検証として書き直す

### Nit

- `_SENTENCE_SPLIT_RE` が「？」「?」で区切らないため、`detect_closing("元気？そろそろ寝るね")` は `False`（再現済み）。Warning 1 の修正に含める
- `create_or_supersede_correction`（`conversation_state.py:343`）で `target_speaker_id=None` を渡すと、`get_open_state_for_ref` が target を絞らず別の相手の訂正を `superseded` にする。PR1 の呼び出し元は無く PR3 の呼び方次第だが、`None` を「全員」の意味で受け付けるのか、禁止するのかを決めておく
- 生成失敗（503）後に相手が同じ質問を再送すると `question_to_yui` が2件になり、節に同じ質問が2行並ぶ。設計 §4 末尾で「重複しうる」と受容済みなので指摘ではないが、節では `content` の同一なものをまとめてよい（`deferral` と同じ扱い）

## 問題が無いことを確認した範囲

- 「応答があった」と「解決した」の分離：`mark_first_response` は `responded_message_id` だけを書き、`status` に触らない。聞き返しで上書きしないことをテストで確認。`resolve_state`／`withdraw_state` を `respond()` から呼ぶ経路は無い
- トランザクション境界：相手の発言由来の状態は `commit`（`conversation.py:144`）で確定し、返答由来の状態は返答の `Message` と同じトランザクション。生成失敗時に相手の発言と質問だけが残る動きは設計 §8 どおり
- 会話ロック：`respond()` 全体が `conversation_locks.hold` の中で、規則の適用と `get_open_states` は同じ会話で重ならない。規則は正規表現のみでイベントループを塞がない
- `presented` の窓：`window_message_ids` は直近 12 件と今の発言。窓の外にあるものだけを直近 5 件出す（設計 §3）
- discrepancy／correction の重複制約：`misdetected` の除外、`asked` 入りの行の扱い、`superseded` の連鎖はテストで固定されている
- migration と model の列・索引は一致。`server_default="0"` は SQLite で問題無い。既存の migration テストが head まで通る
- 秘密情報・権限：新規 API は無く、露出する情報は増えていない

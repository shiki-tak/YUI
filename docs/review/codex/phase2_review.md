## 指摘事項

### 1. [高] 会話を切り替えた後、以前の会話の遅延応答が現在の画面へ混入します

- 場所：[frontend/src/components/ChatPanel.tsx](../../../frontend/src/components/ChatPanel.tsx) 86〜92行目、[frontend/src/App.tsx](../../../frontend/src/App.tsx) 73〜85・134〜139行目、[frontend/src/components/HistoryPanel.tsx](../../../frontend/src/components/HistoryPanel.tsx) 69〜70行目。
- 確認区分：**実コードを模擬フロントエンド環境で実行して再現**。実ブラウザでの操作・発音は未確認です。
- 発生条件：会話Aで送信し、LLM応答を待つ間に履歴から会話Bを開き、その後Aの応答が返る。送信中でも履歴の切り替えは可能です。
- 再現手順：`App` と `ChatPanel` をTypeScriptから変換して実行し、Reactのフック・APIを模擬化。Aの `api.chat()` を保留し、Bの履歴を読み込んでからAの応答を解放しました。
- 観測結果：会話IDはAへ戻る一方、表示メッセージは **Bの履歴＋Aの質問＋Aの遅延返答** となりました。またAの返答への音声取得が要求されました。実際に音が鳴るかは、その後の会話ID変更による停止と取得完了の順序にも依存します。
- 具体的な影響：表示している履歴と、次の送信先となる会話IDが食い違います。Bを続けるつもりの発言をAへ送るおそれがあります。既存のDB行が直接別会話へ移される問題ではありません。
- 関連するコード上の経路：履歴取得にも最新要求の識別がないため、複数の履歴を続けて開くと遅い応答が最後の選択を上書きできます。会話終了の応答も切り替え後の画面を無条件で終了扱いにします。この2経路はコード確認のみです。
- 修正方針：表示対象の世代を管理し、送信・履歴取得・終了の結果を、開始時の会話と世代が現在も一致するときだけ反映する。自動再生にも同じ判定を適用する。新規会話への初回ID付与と、ユーザーによる切り替えは区別してください。

### 2. [中] 音声取得中にアンマウントすると、後から音声の再生が始まります

- 場所：[frontend/src/useSpeechPlayer.ts](../../../frontend/src/useSpeechPlayer.ts) 78〜100・174〜187・241行目。
- 確認区分：**実コードを模擬環境で実行して再現**。Audioはモックであり、実音は出していません。
- 発生条件：音声の取得が完了する前に、このフックを所有するコンポーネントがアンマウントされる。ページ全体の破棄ではなく、同じドキュメント内でのアンマウントが対象です。
- 再現手順：`play()` の音声取得を保留し、登録されたeffectのcleanupを実行。その後、音声取得を成功させました。
- 観測結果：cleanup後に `Audio.play()` が1回呼ばれ、そのAudioには `pause()` が呼ばれませんでした。対照として、同じ取得中に `stop()` を呼んだ場合は再生回数が0でした。
- 原因と影響：cleanupは `teardown()` のみで、`stop()` が行う要求番号の更新をしません。取得後の古さ判定を通過し、所有元が消えた後に新しいAudioとURLが作られます。その後のcleanupもないため、操作できない再生が残り得ます。通常の会話切り替えではフック自体はアンマウントされないため、この指摘と前項は別の経路です。
- 修正方針：アンマウント時にも保留中の要求を無効化し、非同期処理の再開後に破棄済みでないことを確認する。`AudioContext.resume()` の後にも同じ確認を行い、破棄後に解析ノードやアニメーションフレームを登録しないようにする。

### 3. [中] 同時に届いた再生通知で、完了済みの状態が再生中へ戻ります

- 場所：[backend/app/api/conversations.py](../../../backend/app/api/conversations.py) 330〜342行目、[backend/app/agent/delivery.py](../../../backend/app/agent/delivery.py) 20〜36行目。通知元：[frontend/src/useSpeechPlayer.ts](../../../frontend/src/useSpeechPlayer.ts) 68〜75行目。
- 確認区分：**一時DBと実APIで再現**。競合順序を固定するため、メッセージ読込直後に待機する処理をテスト用にメモリ上で差し込みました。
- 再現手順：生成済みの返答について、`playing` 通知のDB読込直後で待機させる。別リクエストで `completed` を通知してコミットした後、先の `playing` を再開する。
- 観測結果：両方ともHTTP 200。最終的なDBの状態は **`playing` かつ `delivery_finished_at` が設定済み** でした。
- 原因と影響：終端状態の判定は各セッションが読み込んだオブジェクト上で行われ、更新時のDB状態を条件にしていません。直列での重複・逆順通知は防げても、古い状態を読み込んだ並行リクエストは終端状態を上書きできます。単一プロセスでも発生し、既知の複数プロセス制約とは別です。フロントは通知を待たずに送るため、短い再生や直後の停止では通知が並行し得ます。
- 修正方針：許可された現在状態をWHERE条件に含める原子的な更新などで、DB上の遷移を保証する。更新後は確定した行を返す。フロント側も遅れて返った通知レスポンスで新しい表示状態を上書きしないようにする。後者はコード確認のみです。

### 4. [中] 再生開始後のエラーで、記録が再生中のまま残ります

- 場所：[frontend/src/useSpeechPlayer.ts](../../../frontend/src/useSpeechPlayer.ts) 197〜204・233・241行目。
- 確認区分：**実コードを模擬環境で実行して再現**。実ブラウザのデコード障害は発生させていません。
- 発生条件：`audio.play()` が成功して `playing` を通知した後、Audioにエラーイベントが発生する。
- 再現手順：音声取得と `play()` を成功させ、開始通知を確認してから `audio.onerror` を呼び出しました。
- 観測結果：再生器はAudioを片付けて表示状態を解除しましたが、通知は **`playing` の1件だけ** で、`aborted` は送られませんでした。
- 具体的な影響：音声は止まっていても、保存された状態は再生中、終了時刻は未設定のままになります。再生中のアンマウントも `teardown()` のみなので、同様に終了通知がありません。このアンマウント時の記録漏れはコード確認です。
- 修正方針：開始済みの再生が異常終了・アンマウントで終わった場合も、中断通知を送る共通処理へまとめる。開始前の失敗では開始時刻を捏造しないこと。また現状は通知の通信失敗も黙って捨てるため、記録の保証範囲を明示し、必要なら未送信通知の再試行・再同期を設ける。再試行は前項の原子的な遷移と組み合わせてください。

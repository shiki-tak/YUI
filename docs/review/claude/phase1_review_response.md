## 総評

指摘8件はすべて実在する不具合でした。誤検知はありません。重要度の高いものは、こちらでも再現手順を組んで確認しています。

- **#1（DBロック）** は、生成中に記憶を訂正すると **5.3秒後に `database is locked`** となることを再現しました。レビューが挙げた発生時間まで一致します。
- **#7（画面の検索）** は、同じ「写真」という語で **画面相当の呼び出しが0件、会話と同じ呼び出しが3件** になることを再現しました。

## 重要度について、レビューと見解が異なる点

### #4 は[中]ではなく[高]と考える

フェーズ1の完了条件「参照した記憶と根拠の会話を開発者が確認できる」を直接崩すためです。2ターン以上の会話では、根拠のポインタが常に誤った発言を指していました。

実装側は当初この機能を「動いている」と報告していましたが、検証したのは1ターンの会話だけでした。複数ターンでの確認が漏れていたことが原因です。

### #2 は[高]ではなく[中]と考える

`subject_speaker_id=NULL` は「キャラクター自身の経験」を表す設計であり、一人の人格が相手をまたいで経験を持ち越すこと自体は意図どおりです。

実際の穴は、`visibility` に「誰が参照してよいか」の次元が無かったことでした。これは複数話者が入るフェーズ4で顕在化します。ただしスキーマの変更を伴うため、DBが小さいうちに対応する判断をしました。

### #3 は実用上のリスクが低いと考える

ローカルで一人が使う前提では起きにくい事象です。ただし対策が安価なため、今回あわせて対応しました。

## 対応した指摘

### #1 [高] 生成中のDBロック

**原因**：発言を `flush()` して SQLite の書き込みロックを取ったまま、LLMの応答を待っていました。SQLiteは書き込みロックを1つしか持てないため、待機中の他の書き込みがロック待ちのタイムアウト（既定5秒）で失敗します。

**対応**：プロンプトを組み終えた時点でコミットし、応答待ちの間はロックを保持しないようにしました。相手の発言はこの時点で確定するため、生成に失敗しても会話履歴には残ります。会話の終了（振り返り）も同じ構造だったため、あわせて直しました。

**確認**：実サーバーで、生成（6.3秒）の最中に記憶を訂正して **HTTP 200 / 0.10秒**。

### #2 [高→中] 非公開記憶が別の相手へ渡る

**対応**：記憶に `visible_to_speaker_id`（誰との会話で参照してよいか）を追加し、`subject_speaker_id`（誰についての記憶か）と別の軸に分けました。ローカル会話では「公開可能な記憶」「相手を限定しない記憶」「この相手に許可された記憶」だけを使います。配信モードは公開可能な記憶のみです。

既存の非公開記憶は、由来した会話の相手をマイグレーションで補完します。手動で追加した記憶（由来する会話が無いもの）は限定しないまま残します。

**確認**：Aとの会話に由来する非公開記憶がBの会話へ渡らないこと、公開記憶は相手を問わず使えること、配信モードで非公開記憶が除外されることをテストで固定しました。

### #3 [中] 会話終了の二重実行

**対応**：終了状態の確定を `UPDATE ... WHERE ended_at IS NULL` の1文で行い、更新できた側だけが振り返りへ進みます。もう一方は409を返します。

あわせて、抽出に失敗した場合は終了状態を戻すようにしました。これを入れないと、失敗した会話が終了済みのまま残り、やり直せなくなるためです（#6を悪化させないため）。

**確認**：実サーバーで同時に2回投げて **200 と 409**、保存された候補は1組のみ。

### #4 [中→高] 記憶候補の根拠

**対応**：会話ログに `[#発言ID]` を付けてLLMへ渡し、候補ごとに根拠の発言を選ばせます。返された番号はその会話の発言に含まれるかを検証し、存在しない番号なら会話内の発言に寄せます。画面では根拠の発言をクリックして本文を開けるようにしました。

**確認**：実モデルで2ターンの会話を試し、「開発者は最近ギターを始めた」がギターの発言を、「次回お会いする約束をした」が別れの挨拶を、それぞれ根拠として指すことを確認しました。

### #7 [中] 画面の記憶検索

**原因**：フロントエンドが話者を送っておらず、バックエンドの既定に頼っていました。検索でも相手を渡していなかったため、会話とは別の条件で検索していました。

**対応**：フロントに自分の識別情報（`source` と `external_id`）を定数として持たせ、会話でも検索でも明示的に送るようにしました。

**確認**：同じ「写真」で **0件 → 3件**。

# 再評価（phase1_review2.md）への対応

対象：[docs/review/codex/phase1_review2.md](../codex/phase1_review2.md)
作成日：2026-09-06

## 評価

追加指摘4件はすべて再現しました。文書とテストへの批判も、いずれも当たっています。

| 指摘 | 再現結果 |
| --- | --- |
| 1. 候補の移行漏れ | 旧形式DBの未採用候補が移行後も `visible_to_speaker_id=NULL` |
| 2. 同一会話での順序逆転 | 履歴が「質問A → 質問B → 返答B → 返答A」になった |
| 3. 中断後に再試行不可 | 候補0件のまま再試行が409 |
| 4. 不正IDの付け替え | 「写真が趣味」の根拠が「今日はここまで」になった |

指摘1については、対応時点の `data/yui.db` に未採用のまま `visible_to_speaker_id=NULL` の候補が5件残っていました。理論上の問題ではなく、実データが該当していました。

指摘2は、こちらが持ち込んだ後退です。修正前は DB の書き込みロックが偶然の直列化として働いていました。ロックを外したときに、代わりの順序制御を用意していませんでした。硬い失敗を、静かな履歴破損に置き換えたことになります。

## 対応内容

### 1. 記憶候補の参照範囲の補完

新しいマイグレーション（`a71c525f0285`）で、`memory_candidates` の参照範囲を由来した会話の相手から補完します。相手を特定できない候補（利用者の発言が無い会話）は NULL のまま残します。

実データの5件が正しく補完されたことを確認しました。振り返りで新しく作る候補が必ず参照範囲を持つことは、テストで固定しています。

### 2. 会話単位の直列化

`app/agent/turn_lock.py` を追加し、会話 id ごとのプロセス内ロックで直列化しました。DB の書き込みロックとは切り離してあるため、他の会話や記憶の訂正は止まりません。発言の保存もロックの内側で行い、到着順がそのまま履歴の順になります。振り返りにも同じロックを掛けています。

設計書の発話管理（asyncio による順序管理）のうち、フェーズ1で必要な範囲にあたります。MVP は単一プロセスのため、プロセス内のロックで足ります。複数プロセスに分ける段階では、DB か外部のロックへ置き換える必要があります。

実サーバーで同じ会話へ同時に2つ送り、「質問A → 返答A → 質問B → 返答B」の順になることを確認しました。

### 3. 振り返りの中断からの回収

会話に `reflection_started_at` と `reflection_completed_at` を追加し、「処理中」と「完了」を分けました。

- 開始の確定は 1 文の UPDATE で行い、同時実行では片方だけを通します。
- 完了時にだけ `ended_at` を設定します。
- `LLMError` では開始を取り消します。
- 中断やプロセス停止で開始だけが残った場合は、`reflection_stale_seconds`（既定180秒）を過ぎたらやり直せます。LLM 自体のタイムアウトより長くとっています。

完了した振り返りは、時間が経っても再実行しません。

### 4. 不正な根拠IDの扱い

直近の発言へ寄せる処理をやめ、`source_message_id` を NULL のまま残すようにしました。無関係な発言を確かな根拠として保存するより、未確認として残すほうが正しいためです。画面では記憶・候補の双方に「根拠未確認」と表示し、採用前に気づけるようにしました。

## テストの修正

指摘のとおり、`test_candidate_keeps_its_own_source_message` は `conversation_id` を渡しておらず、2回の発言が別々の会話になっていました。会話1には発言が1つしかないため、アサーションは自明に通っていました。複数ターンの検証になっていません。

ヘルパー `_say()` に `conversation_id` を追加し、同じ会話の2ターン目であることを明示的に確認するよう直しました。実モデルでの手動確認は複数ターンで行っていましたが、自動テストがそれを守っていなかったのが原因です。

再評価で見つかった4件についても、再発検知テストを追加しました（合計26件）。

## 修正の途中で見つかった不具合

振り返りの開始判定に日時の比較を入れたところ、`can't compare offset-naive and offset-aware datetimes` で失敗しました。SQLite は timezone を落として返すため、SQLAlchemy が UPDATE の条件を Python 側で評価しようとして型が食い違います。条件の判定を SQL に任せる（`synchronize_session=False`）ことで解消しました。

同種の問題は記憶検索側にもあり、そちらは読み出し時に UTC を補う処理で回避しています。日時の扱いは今後も落とし穴になりやすい箇所です。

## 残っている課題

#5・#6・#8 は引き続き未対応です。特に #6（不正な振り返り出力を成功として扱う）は、上の訂正のとおり解消していません。壊れた出力は `200 []` で完了扱いになり、完了した振り返りは再実行できないため、その会話からの再抽出はできません。

## 重要度について、レビューと見解が異なる点

### #4 は[中]ではなく[高]と考える

フェーズ1の完了条件「参照した記憶と根拠の会話を開発者が確認できる」を直接崩すためです。2ターン以上の会話では、根拠のポインタが常に誤った発言を指していました。

実装側は当初この機能を「動いている」と報告していましたが、検証したのは1ターンの会話だけでした。複数ターンでの確認が漏れていたことが原因です。

### #2 は[高]ではなく[中]と考える

`subject_speaker_id=NULL` は「キャラクター自身の経験」を表す設計であり、一人の人格が相手をまたいで経験を持ち越すこと自体は意図どおりです。

実際の穴は、`visibility` に「誰が参照してよいか」の次元が無かったことでした。これは複数話者が入るフェーズ4で顕在化します。ただしスキーマの変更を伴うため、DBが小さいうちに対応する判断をしました。

### #3 は実用上のリスクが低いと考える

ローカルで一人が使う前提では起きにくい事象です。ただし対策が安価なため、今回あわせて対応しました。

## 対応した指摘

### #1 [高] 生成中のDBロック

**原因**：発言を `flush()` して SQLite の書き込みロックを取ったまま、LLMの応答を待っていました。SQLiteは書き込みロックを1つしか持てないため、待機中の他の書き込みがロック待ちのタイムアウト（既定5秒）で失敗します。

**対応**：プロンプトを組み終えた時点でコミットし、応答待ちの間はロックを保持しないようにしました。相手の発言はこの時点で確定するため、生成に失敗しても会話履歴には残ります。会話の終了（振り返り）も同じ構造だったため、あわせて直しました。

**確認**：実サーバーで、生成（6.3秒）の最中に記憶を訂正して **HTTP 200 / 0.10秒**。

### #2 [高→中] 非公開記憶が別の相手へ渡る

**対応**：記憶に `visible_to_speaker_id`（誰との会話で参照してよいか）を追加し、`subject_speaker_id`（誰についての記憶か）と別の軸に分けました。ローカル会話では「公開可能な記憶」「相手を限定しない記憶」「この相手に許可された記憶」だけを使います。配信モードは公開可能な記憶のみです。

既存の非公開記憶は、由来した会話の相手をマイグレーションで補完します。手動で追加した記憶（由来する会話が無いもの）は限定しないまま残します。

**確認**：Aとの会話に由来する非公開記憶がBの会話へ渡らないこと、公開記憶は相手を問わず使えること、配信モードで非公開記憶が除外されることをテストで固定しました。

### #3 [中] 会話終了の二重実行

**対応**：終了状態の確定を `UPDATE ... WHERE ended_at IS NULL` の1文で行い、更新できた側だけが振り返りへ進みます。もう一方は409を返します。

あわせて、抽出に失敗した場合は終了状態を戻すようにしました。これを入れないと、失敗した会話が終了済みのまま残り、やり直せなくなるためです（#6を悪化させないため）。

**確認**：実サーバーで同時に2回投げて **200 と 409**、保存された候補は1組のみ。

### #4 [中→高] 記憶候補の根拠

**対応**：会話ログに `[#発言ID]` を付けてLLMへ渡し、候補ごとに根拠の発言を選ばせます。返された番号はその会話の発言に含まれるかを検証し、存在しない番号なら会話内の発言に寄せます。画面では根拠の発言をクリックして本文を開けるようにしました。

**確認**：実モデルで2ターンの会話を試し、「開発者は最近ギターを始めた」がギターの発言を、「次回お会いする約束をした」が別れの挨拶を、それぞれ根拠として指すことを確認しました。

### #7 [中] 画面の記憶検索

**原因**：フロントエンドが話者を送っておらず、バックエンドの既定に頼っていました。検索でも相手を渡していなかったため、会話とは別の条件で検索していました。

**対応**：フロントに自分の識別情報（`source` と `external_id`）を定数として持たせ、会話でも検索でも明示的に送るようにしました。

**確認**：同じ「写真」で **0件 → 3件**。

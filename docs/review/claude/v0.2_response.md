## 2回目のレビュー（codex、`v0.2_review.md`）への対応

**結論の確認：** レビュー自身が「Critical は無い」としており、こちらの確認でも同じでした。指摘は Warning 4件と Nit 3件です。

### Warning 1：改行を文の区切りとして扱わないため、延期の話題が前の行を飲み込み、終了の合図を取りこぼす

**妥当。修正した。**

#### 確認したこと

指摘どおり再現しました。

```
detect_deferral_topic("今日は疲れた\n映画の話はまた今度")  →  "疲れた\n映画"
detect_closing("今日は楽しかった\nそろそろ寝るね")          →  False
```

画面の入力欄は `textarea` で、Enter は改行、送信は ⌘/Ctrl+Enter（`ChatPanel.tsx`）なので、通常操作で複数行の発言が届きます。1回目のレビューで「最後の文だけを見る」形に直した際、区切り文字に句点・感嘆符・疑問符しか入れておらず、改行を見落としていました。

#### 直し方

`_SENTENCE_SPLIT_RE` に `\n` を追加しました（[conversation_state.py:100](../../../backend/app/agent/conversation_state.py#L100)）。あわせて `_DEFERRAL_RE` の topic の文字クラスからも `\n` を除外し、文をまたいで topic が伸びないようにしています。

#### 確認

`test_detect_deferral_topic_requires_topic_and_sentence_ending` と `test_detect_closing_requires_sentence_ending_form` に、改行区切りの例をそれぞれ追加しました。修正前のコードに戻すと両方失敗することを確認済みです。

### Warning 2：「そうですか」「そうなんですか」が相手の質問として登録される

**妥当。修正した。**

#### 確認したこと

再現しました。

```
'そうですか。'          True
'そうですか'            True
'なるほど、そうですか！'  True
'へえ、そうなんですか'    True
```

計画 §3 の語彙は「ですか」を含みませんが、実装が独自に広げていました。`is_acknowledgement_only` は完全一致（6文字以内）を要求するため、「なるほど、そうですか！」のように前置きが付く形は弾けません。

#### 直し方

`_ACKNOWLEDGEMENT_QUESTION_RE`（`そう(なん)?ですか` ＋ 句読点）を新設し、`detect_question` の入口でこれに一致する発言を除外しました（[conversation_state.py:118-132](../../../backend/app/agent/conversation_state.py#L118-L132)）。`is_acknowledgement_only` の完全一致とは別に、文末だけを見て弾く形にしています。「ですか」自体は語彙から外していません——「山は好きですか」のような疑問文まで拾えなくなるのを避けるためです。

最初に書いた正規表現は句点（`。`）を許しておらず、感嘆符（`！`）にしか対応していませんでした。追加したテストの `assert not detect_question("そうですか。")` がこれで一度落ち、`[。.！!]*` に直してから通しています。

#### 確認

`test_detect_question_matches_sentence_ending_forms` に4つの再現例と、「ですか」自体は引き続き拾う確認（`山は好きですか`）を追加しました。

### Warning 3：質問本文が無制限に system prompt へ入る

**妥当。修正した。**

#### 確認したこと

再現しました。`ChatRequest.text` の上限は4000文字で、4000文字の質問1件だけで「この会話で」節が4000文字を超えます。`presented` は200文字で切っている一方、`question_to_yui`／`question_to_partner`／`closing` は全文を保持していました。

#### 直し方

`CONTENT_LIMIT = 200` を新設し、4箇所の `content=text` をすべて `content=text[:CONTENT_LIMIT]` に揃えました（[conversation_state.py:36](../../../backend/app/agent/conversation_state.py#L36)）。`presented` の `200` もこの定数を参照する形に直しています。

#### 確認

`test_long_question_is_truncated_in_content_and_prompt` を追加。ChatRequest の上限（4000文字）に収まる長文の質問を送り、保存された `content` が200文字以内であることを確認します。

### Warning 4：`question_to_yui` の target 絞り込み（YUI の返答側）を検出できるテストが無い

**妥当。修正した。**

#### 確認したこと

指摘の変異検証を実際に試しました。`apply_character_message_rules` の `get_open_states` から `target_speaker_id` を落としても、既存の `test_state_targeted_at_one_speaker_is_not_affected_by_another` は通ったままでした。理由は、その検証が「A自身のターンの返答が最初の応答候補になる」経路にしか当たっておらず、絞り込みが効くのは「Aの質問が `responded` 空のまま残る場合」（＝Aの生成が失敗したとき）だけだったためです。

#### 直し方

コードは変更していません。テストの抜けなので、テストを足しました。`test_yuis_reply_failure_then_b_does_not_answer_a_question_to_yui` を追加し、`fake_llm.chat` を `LLMError` に差し替えてAの返答を503で失敗させ、その後にBのターンを実行して、Aの `question_to_yui` が `responded_message_id is None` のままであることを直接見る形にしました（[test_conversation_state.py:375-430](../../../backend/tests/test_conversation_state.py#L375-L430)）。

#### 確認

このテストを追加したうえで、`apply_character_message_rules` の target 絞り込みを一時的に外して実行し、**テストが実際に失敗する**ことを確認してから元に戻しました。

このとき、`git checkout --` で作業ファイルを戻したところ、直前に加えていた Warning 1〜3 の未コミットの修正も一緒に失われる事故がありました。すぐに気づいて3件とも再適用し、最終的な diff とテスト結果で失われていないことを確認しています。以後、こうした一時的な変更の確認には `git checkout` ではなく退避を使うべきでした。

### Nit：節での質問の重複

**妥当。修正した。**

生成失敗（503）後に相手が同じ質問を再送すると、規則は重複制約を置かないため同じ本文の `question_to_yui` が複数件できます（設計 §4 末尾で許容されている挙動）。節に出すときは `deferral`／`closing` と同じく、同じ本文をまとめるようにしました。`test_prompt_section_deduplicates_repeated_questions` を追加しています。

### 「対象と確認方法」欄で報告された、修正不要と判断した点

レビュー本文の「diff から読み取った意図と、設計書とのズレ」節にある3点は、レビュー自身が「不具合ではない」としており、こちらでも同じ判断です。

| 項目 | 判断 |
| --- | --- |
| 規則の適用位置が「取得の後」ではなく「相手の発言保存直後」 | 直さない。規則は履歴・記憶を参照しないため結果は変わらない |
| `question_to_yui` の語彙が計画 §3 より広い（「ですか」「かしら」等） | 「ですか」は Warning 2 の対応で相づちの場合だけ除外。「かしら」等の残りは、質問検出の recall を優先する判断として維持する |
| `/end` での `expired` 化が未配線 | 直さない。PR4 の範囲。`_ensure_open` が終了済み会話への発言を拒むため、開いたままでも副作用は無い |
| `create_or_supersede_correction` に `target_speaker_id=None` を渡すと絞り込みが効かない（Nit） | 未対応。PR1 に呼び出し元が無く、PR3 の呼び方次第。PR3 着手時に「`None` を全員の意味で受け付けるか禁止するか」を決める |

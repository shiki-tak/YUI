## 指摘1：`active_goals` が現在時刻を UTC へそろえず、実行日時を誤判定する

**妥当。修正した。再現も確認した。**

### 確認したこと

`due_at` は `normalize_due_at` で保存前に UTC へ直していましたが、**比較に使う
`now` はそのまま SQL へ渡していました**。SQLite は timezone を落として比較する
ため、日本時間で渡された `now` は、その壁時計の値が UTC として扱われます。

指摘の表のとおり、同じ瞬間でも表記によって結果が変わります。基準日時 9/13 15:30
UTC の目標に対し、9/13 15:00 UTC（まだ実行してはいけない）を同じ瞬間の
9/14 00:00 JST として渡すと、実行してよいと判定されました。

**保存側だけそろえても足りない**、というのが今回の穴です。記憶の `occurred_at`
で踏んだずれ（日本時間 00:30 の発言が前日扱いになる）と同じ形が、比較側に
残っていました。

### 直し方

`as_utc()` を切り出し、保存（`normalize_due_at`）と比較（`active_goals`）の
両方で同じ関数を通すようにしました（[goal.py](../../../backend/app/agent/goal.py)）。

- timezone を持つ値は UTC へ直す。
- timezone を持たない値は UTC として解釈する。保存が UTC なので、DB から読み
  戻した値をそのまま渡しても同じ基準になります（`config.to_local` と同じ約束）。

`now` を受け取る関数は今後も増えます（評価に `advance_time` を足す PR3、期限
切れを判定する PR9）。経路ごとに直すのではなく、**時刻を受け取る側が1か所で
そろえる**形にしました。

### 確認

`tests/test_goal.py::test_the_same_moment_is_judged_the_same_in_any_timezone` を
追加しました。同じ瞬間を UTC・UTC+9・UTC−7 の3通りで渡し、基準日時の前後で
判定が一致することを見ます。あわせて次の2つも入れています。

- 境界：`now == due_at` は「以降」に含める。
- timezone を持たない `now` を UTC として扱う。

`now` の正規化を戻すと、このテストが失敗することを確認しました（修正前の状態を
再現して1件失敗、戻して11件成功）。

## 補強：配信で相手を指定した目標

指摘ではなく「補強できる」とされた項目のうち、**配信で相手を指定するケース**を
テストに足しました（`test_a_public_goal_about_someone_stays_with_that_person`）。

公開してよいことと、誰に対する目標かは別の軸です。公開の印だけを見ると、本人が

すでに相手で絞っていましたが、**その組み合わせを測っていませんでした**。

相手の指定と公開範囲の総当たりまでは広げていません。行動選択が入る PR7 で、
評価シナリオ側から同じ組み合わせを通します。

- **ORM を直接操作すれば `normalize_due_at` を迂回できる。** PR4 で更新処理を
  足すときに同じ検査を通します。DB 制約は入れていません。SQLite の batch
  マイグレーションで扱いが増えるためで、判断は [phase4.md](../../plan/phase4.md) の PR4 に書いています。
- **`snapshot` に `source_conversation_id` を含めていない。** 変更しない項目で、
  目標本体に残ります。`character_state.snapshot` と同じ扱いです。
- **schema 一致テストが外部キー・既定値・索引の構成列まで見ていない。** 列名・
  型・NULL 可否・索引名までの比較です。手書きマイグレーションのずれを見つける
  目的には足りていると判断しました。

## 指摘1［高］：手順に適用されない期待条件が受理され、自動合格に数えられる

**妥当。修正した。再現も確認した。**

### 確認したこと

指摘のとおりでした。`say` に `expect_goal_any`（振り返り用）を書いた
シナリオを流すと、`has_machine_checks` は真、実行された判定は空、
`attempt.ok` は真、`human_only` は偽になりました。**期待を書いたのに一度も
判定せず、機械判定の成功数に入ります。**

同じ形は他の組み合わせでも起きます。`reflect` に `expect_memories`、
`accept_goal` に `expect_any`、`advance_time` に `expect_goals` など、
指定できる場所が手順の種類と結び付いていませんでした。

### 直し方

手順の種類ごとに書ける指定を表にし、**読み込みの時点で弾く**ようにしました
（[scenario.py](../../../backend/app/evaluation/scenario.py)）。実モデルを何度も呼んでから気づくと高くつくため、
既存の書き間違いの検査と同じ位置に置いています。

- `say` / `start_conversation`：返答に対する期待（記憶・状態・目標・語・繰り返し）
- `reflect`：候補に対する期待と採用の指定
- `correct_memory` / `delete_memory`：対象と、印が付く目標
- `accept_goal`：対象と名前、`advance_time`：日数
- `new_conversation` / `restart`：なし

`human_check` はどの手順にも書けます（人が読む欄なので）。

### 確認

- `test_expectations_that_do_not_apply_to_the_step_are_rejected`：5種類の
  組み合わせが読み込みで止まること。
- `test_no_bundled_scenario_passes_without_executing_a_check`：同梱の全43本を
  モックで流し、機械判定ありと数えたシナリオが**判定を1つも実行しないまま
  終わっていない**ことを見ます。指摘の「機械判定ありと分類した条件が、実行時に
  判定結果へ対応することも検査する」に対応します。

## 指摘2［中］：訂正波及シナリオの目標が、訂正する記憶を根拠に持っていない

**妥当。修正した。**

### 確認したこと

`GoalSpec` に根拠を指定する場所がなく、`corrected-basis-marks-the-goal` の
目標は `basis_memory_ids=None`・`source_conversation_id=None` でした。
訂正の波及そのものは動きますが、**この目標は対象になりません**。

測定として成立していませんでした。`expect_not_goals`（渡っていないこと）は、
目標を一切渡さない実装でも通ります。いまは `start_conversation` の未実装失敗に
隠れていますが、PR7 が入れば「何も起きていないのに通る」状態になります。

### 直し方

2つ入れました。

1. `GoalSpec.basis`（記憶の鍵の並び）。投入のときに実際のIDへ直します。
   シナリオでは `basis = ["movie-plan"]` と書き、訂正する記憶と結び付けました。
2. `expect_marked_goals`。**印が付いたことを記録で確かめます。** 訂正・削除の
   手順が、波及で印を付けた目標の鍵を返すようにし
   （`steps.MemoryChange`）、期待と突き合わせます。

否定条件だけに頼らない形にしたのは、指摘の「対象の存在、採用状態、根拠、日時
等の前提を検査し、抑制理由も別に観測すべき」に沿ったものです。

### 確認

`test_correcting_the_basis_is_measured_by_the_mark_not_by_absence` で、根拠を
結び付けた目標では印が付き、**結び付けていない目標では判定が落ちる**ことを
見ます。前提が欠けたまま通らないことを、テストの側で押さえました。

## 指摘3［中］：時間を進めた後の発言が実時計の日付で保存される

**妥当。修正した。再現も確認した。**

### 確認したこと

30日進めて「昨日、映画を見たよ」と発言し、振り返りへ渡るプロンプトを見ました。

```
[#1／2026-09-08] 開発者: 昨日、映画を見たよ        ← 実時計
振り返りを行っている日: 2026-10-08                  ← 進めた時計
```

振り返りは「相対的な日付は、その言い方が出てきた発言の日付から数える」設計
なので、**1か月ずれた入力を渡していました**。

### 直し方

出来事の時刻と、監査の記録を分けました。

- 発言（`messages.created_at`）は、会話に渡した現在時刻と同じ基準で保存する。
- 評価で採用した記憶（`memories.created_at`）も同じ。検索の減衰が、まだ作られて
  いない記憶を新しいものとして扱わないため。
- 再生の記録（`delivery_started_at` / `delivery_finished_at`）は実時計のまま。
  いつ鳴らしたかは監査の記録で、会話の中の時間の進み方とは別のもの。

通常の呼び出しは `now` を渡さないので、これまでと同じ実時計で動きます。

### 確認

`test_the_advanced_clock_reaches_the_saved_message` で、会話ログの発言日と
振り返りが「今日」とする日が揃うことを見ます。

## 指摘4［低］：基準測定の失敗原因の説明が、ログと異なる

**妥当。訂正した。**

レポートを読み直しました。`correction-changes-the-next-answer` の不合格は
[ISSUE-022](../../issues/issues.md#issue-022) ではありません。返答は「開発さんが最近**红茶**をよく飲むのが
お好きだってことを覚えています」で、**訂正後の好みは覚えています**。期待語
「紅茶」に一致しなかったのは、簡体字で書いたためです。

[phase4.md](../../plan/phase4.md) の基準値表を、次の内訳へ訂正しました。

- 約束を覚えていない：2試行（[ISSUE-022](../../issues/issues.md#issue-022)）
- 訂正後の表記の不一致：1試行
- 過剰抽出：3試行（[ISSUE-021](../../issues/issues.md#issue-021)）

あわせて、分母の84が「機械判定を持つ28シナリオ×3回」であること（99試行すべてを
自動採点した数ではないこと）も明記しました。

**この1件は、指摘6で挙げられた「expect_none / expect_any は言い換えを検知
しない」の実例でもあります。** 訂正が反映されているかを測りたいのに、判定して
いるのは表記の一致です。意味が通っている返答を落としており、[ISSUE-022](../../issues/issues.md#issue-022) の
修正方針に書いた「否定表現を並べる形は誤判定を起こす」と同じ構図です。

## 対応しなかったもの

指摘ではなく「限界」として挙がったもののうち、後続の PR で扱うと判断したものです。

- **抽出 → 採用 → 期限後の参照を一続きに測るシナリオ。** いまはどのシナリオも
  事前投入から始まり、`adopted-goal-is-asked-later` も事前作成した候補の採用です。
  会話から目標を抽出する経路は PR6 で入るため、そこで `accept_goal` の
  `goal_key` を使った通しのシナリオを足します。**フェーズ3で5回続けて指摘された
  形と同じなので、PR6 の完了条件に含めます。**
- **`does-not-pile-up-questions` が「渡した目標の数」しか測れないこと。**
  実際に選んだ行動は `run_records.selected_action` に残る予定で、書き手が入るのは
  PR7 です。そこで機械判定へ接続します。それまでは人手欄のままです。
- **完了条件3・6の機械判定が目標の参照だけであること。** 実行時刻・完了時刻の
  検査は PR8・PR9、人格の前後比較は PR10 の測定で扱います。
- **`selected_action` が未記録であることと、待機を選んだことを同一視しない。**
  指摘のとおりです。PR7 で待機も明示的に記録します。

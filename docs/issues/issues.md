## ISSUE-001

**空白だけの本文が、空の候補として保存される**

- 状態：完了（2026-09-07）
- 重要度：低
- 種別：不具合
- 出所：Codex 5回目のレビュー
- 場所：[backend/app/agent/reflection.py](../../backend/app/agent/reflection.py)

### 内容

候補の本文は `min_length=1` で検証しているが、検証は空白を除去する前に行い、保存時に `strip()` している。そのため空白・改行・タブだけの本文は検証を通り、本文が空の候補として保存される。

### 再現

LLMが `[{"kind":"promise","content":"   \n\t", ...}]` を返すと、**200・`content=""` の候補1件・会話終了・再試行409** になる。利用できる本文が無いのに抽出成功として扱われる。再現済み。

### 修正方針

本文を正規化してから最小長を検証する。空白だけなら既存の `ReflectionParseError` へ流し、正常な候補と混在しても全体を失敗にする。空白・改行・タブのみの入力を再発検知テストへ追加する。

### 対応

`CandidatePayload.content` に `mode="before"` の検証を足し、最小長を見る前に空白を落とすようにした。空白だけの本文は既存の `ReflectionParseError` へ流れ、正常な候補と混ざっていても全体が失敗になる。

確認：`tests/test_review_fixes.py::test_invalid_candidate_element_is_reported` に空白・改行・タブだけの場合を追加した。修正を戻すとこの1件が失敗することを確認済み。

## ISSUE-002

**明示的な約束を、振り返りが取りこぼすことがある**

- 状態：完了（2026-09-07）
- 重要度：高（2026-09-07 に中から引き上げ。フェーズ3の完了条件「約束・共有経験を参照できる」に直結するため）
- 種別：品質
- 出所：実装中の観測、Codex 5回目のレビューでも継続評価が必要と指摘

### 内容

抽出の指示文には「次に話すと決めたことは必ず promise として残す」とあるが、実モデルが `[]` を返して候補が1件も出ないことがある。

### 再現

「最近はランニングを始めたよ。朝5キロ走ってる。次はシューズの話をしよう」という発言で、qwen3.5:9b が3回とも `[]` を返した。会話を長くしても変わらなかった。

一方、同じ構造でも「実は最近ギターを始めたんだ。指が痛くてなかなか進まないけど楽しいよ／好きなバンドのバラードかな。次はコードの練習の話をしよう」では候補が出る。入力の内容によってモデルの判断が変わる。

解析処理の変更に起因するものではないことは確認済み（同じ会話文を同条件で流すと候補が出る）。

### 影響

記憶を作る経路はこの振り返り一本しかない。取りこぼすと、その会話の経験は残らず、失われたことに気づく手段もない。フェーズ1の中心機能の品質に関わる。

### 修正方針

まず [ISSUE-006](#issue-006) の評価用会話を整え、期待する約束・経験が候補に含まれるかを測る。そのうえで抽出の指示文を調整する。形式検証が通ることと、残すべき内容を実際に抽出できることは別の評価である。

### 測定できるようになった（2026-09-07）

[ISSUE-006](#issue-006) の評価用会話に `promise-running-shoes`（この再現例）と
`promise-guitar-chords`（候補が出ていた対照）を入れた。次で頻度を測れる。

```sh
.venv/bin/python -m app.evaluation.run --aspect reflection --repeat 5
```

初回の実測（qwen3.5:9b、人格の版 2026-09-06.2、2回）では
`promise-running-shoes` が **0/2**。取りこぼしは再現している。抽出の指示文の
調整は、この数字を前後で比べて判断する。

### 対応（2026-09-07）

5回ずつ流して測り、抽出の指示文を調整した。同じ条件で前後を比べている
（qwen3.5:9b、人格の版 2026-09-06.2、`--aspect reflection --repeat 5`）。

| シナリオ | 調整前 | 調整後 |
| --- | ---: | ---: |
| promise-running-shoes（ISSUE-002 の再現例） | 0 / 5 | **5 / 5** |
| promise-guitar-chords（候補が出ていた対照） | 0 / 5 | **5 / 5** |
| experience-is-kept（単発の出来事） | 0 / 5 | **5 / 5** |
| small-talk-is-not-kept（何も残さない） | 5 / 5 | 5 / 5 |
| 合計 | 5 / 20 | **20 / 20** |

**分かったこと**：候補が出ていなかったのではなく、`promise` という種別が
一度も選ばれていなかった（10試行で0件）。経験や相手についての候補は出ていた。

指示文の変更点。

- `promise` の定義を具体化した。「次は◯◯の話をしよう」のような**話題の予告**も
  含むこと、会話に出てきたら他に何を出すかに関わらず必ず1件残すことを明記した。
- 相手が話した出来事は、一度しか出てこなくても残すことを明記した
  （`experience-is-kept` が 0/5 だった原因）。
- 「その場限りのやり取りは出さない」が上の2つを飲み込まないよう、例外を書いた。
- キャラクター自身の経験や過去を作らない規則を、種別によらない形にした。

`small-talk-is-not-kept` を 5/5 のまま保てているので、取りこぼしを直すために
何でも候補にする方向へは倒れていない。この確認のために、評価側へ「候補が
1件も出ないこと」を確かめる指定（`expect_empty`）を足した。

**残っている risk**：キャラクター自身の架空の事実が候補に混ざることがある。
調整前は20試行中2件（「YUI は以前楽器を習った経験がある」等）、調整後は1件
（「YUI はペットを飼っており…」）。減ったが無くなっていない。候補は開発者が
採用する前に画面へ出るため記憶にはならないが、機械では検知していない。
評価用会話の「人が見る点」で確認する。

## ISSUE-003

**会話履歴を画面から読み直せない**

- 状態：完了（2026-09-07）
- 重要度：中
- 種別：未実装

### 内容

`GET /api/conversations` と `/api/conversations/{id}` はあるが、フロントエンドから呼んでいない。過去の会話を開く導線が無く、「終了して振り返る」を押すと画面上の会話は消える。DBには残るので失われてはいない。

設計書フェーズ1の実装内容4「SQLiteへ会話履歴を保存する」は満たしているが、保存したものを確認できない。

### 修正方針

会話一覧と、選んだ会話の詳細を表示する。終了済みの会話は読み取り専用として開く。

### 対応

`frontend/src/components/HistoryPanel.tsx` に「会話履歴」タブを追加し、会話を選ぶと発言を読み直せるようにした。

- 未終了の会話は開いて続きを話せる。終了済み・振り返り中は読み取り専用で開く。
- 終了しても画面から会話を消さず、読み取り専用へ切り替える。抽出された候補と、その元になった会話を見比べられる。
- 過去の返答も「根拠」を開ける。その場で生成した返答と違い点数・理由は保存していないため、実行記録に残した記憶IDから内容を引き直す。このために `GET /api/memories/{memory_id}` を追加した（訂正・削除済みでも返す。当時それを渡した事実は変わらないため）。
- API の日時に timezone を付けて返すようにした（`schemas.UtcDatetime`）。保存は UTC だが SQLite が timezone を落とすため、そのままでは画面が地域時刻として解釈し、表示が9時間ずれていた。

確認：`backend/tests/test_history.py` を追加（9件）。pytest 49件成功、ruff・TypeScript の型チェック・Vite ビルド成功。実データに対して一覧・詳細・実行記録・記憶IDの取得を確認した。

## ISSUE-004

**記憶検索の「時刻」が減衰のみで、occurred_at を埋めていない**

- 状態：完了（2026-09-07、振り返りで埋めるところまで）
- 重要度：中
- 種別：未実装

### 内容

設計書フェーズ1の実装内容6は「相手・時刻・話題のキーワードで関連する記憶を取り出し」だが、実装している時刻の扱いは「新しい記憶をわずかに優先する」減衰だけである。

`memories.occurred_at`（いつの出来事か）の列はあるが、振り返りの抽出では埋めていない。手動のAPIからしか入らない。「昨日話したこと」のような時間を指す問いかけも解釈しない。

### 修正方針

振り返りで出来事の日時を推定して `occurred_at` に入れる。検索側では、問いかけに含まれる時間表現を範囲条件として扱う。フェーズ3（3B）の完了条件「訂正後、古い情報を現在の事実として回答しない」は、いつの話かを区別できないと確認しにくい。

### 対応（範囲を絞った）

**振り返りで `occurred_at` を埋めるところまで**を行った。問いかけの時間表現を検索の範囲条件にする部分はフェーズ4へ回す（開発者と合意済み）。訂正の判定には「いつの話か」が保存されていれば足り、時間表現の解釈は自発性の段階で効いてくるため。

- 振り返りに渡す入力の冒頭へ今日の日付を入れた。「先週」「昨日」を日付へ直すには今日が何日かが要る。
- 候補にも `occurred_at` を追加した（Alembic `66c78282e48e`）。記憶側の列は初期スキーマからあるが、これまで手動のAPIからしか入らなかった。
- **読み取れない日付は「日付なし」として扱う**。振り返り全体は失敗させない。日付は多くの記憶で決まらないもので、null が正しい値であるため。ただし、読めない値や未来の日付を、それらしい日付へ寄せることはしない。**間違った日付は、日付が無いことより悪い。**
- 地域時刻のその日の始まりを **UTC に直して保存**する。SQLite は timezone を落とすため、他の日時と同じく UTC で保存しないと、読み戻したときに9時間ずれる（[ISSUE-003](#issue-003) と同じ問題）。実装中にこのずれを作ってしまい、テストで検知して直した。

### 確認

実モデル（qwen3.5:9b、「先週、実家の犬が18歳になった」を5回）。

| 指示文 | 日付が入った回数 |
| --- | ---: |
| 「分かる場合だけ」と書いた | 2 / 5 |
| 「手がかりがあれば**必ず**入れる」と書いた | **4 / 5** |

入った日付はいずれも 2026-09-01（実行日 2026-09-07 の「先週」）で正しかった。振り返りの観点は 22/24 で、他のシナリオへの悪影響は出ていない。

`backend/tests/test_occurred_at.py` を追加（16件）。読み取れない値・未来の日付・空・null を日付なしとして扱うこと、地域時刻での日付が合っていること、候補から記憶へ引き継がれることを固定した。

残り：問いかけの時間表現（「昨日話したこと」）を検索の範囲条件として扱う部分はフェーズ4。

## ISSUE-006

**評価用会話が未整備**

- 状態：完了（2026-09-07）
- 重要度：高（2026-09-07 に中から引き上げ。フェーズ3の3Aは人格版の比較が前提のため）
- 種別：未整備

### 内容

設計書は「評価用会話の整備」を全フェーズで継続する作業とし、「記憶、人格、根拠、繰り返しなどの観点で用意」としている。フェーズ3の3A（人格版の比較）は、この評価用会話が無いと着手できない。

現在あるのは pytest 41件だが、これは実装の振る舞いを固定するもので、人格や記憶利用の質を測る会話集ではない。

### 影響

モデルやプロンプトを変えたときに、良くなったか悪くなったかを判断できない。[ISSUE-002](#issue-002) の取りこぼしも、これが無いと頻度を測れない。

### 修正方針

観点ごとに会話と期待する振る舞いを用意する。少なくとも次を含める。

- 記憶：保存した経験・約束を、別の会話で引けるか
- 根拠：返答が渡した記憶の範囲に収まっているか
- 人格：口調と「知らないことは正直に言う」が保たれているか
- 振り返り：残すべき経験・約束が候補に含まれるか
- 繰り返し：同じ話を繰り返していないか

### 対応

`backend/evals/scenarios/*.toml` に観点ごとのシナリオを置き、`app/evaluation/`
で実モデルに流してレポートを出すようにした。実行は
`.venv/bin/python -m app.evaluation.run --repeat 3`。

- 上の5観点で15シナリオ。事前に入れる記憶、入力の並び、期待する振る舞いを持つ。
- 機械で判定するもの：渡した記憶（実行記録の参照記憶と突き合わせ）、返答に
  含まれてほしい／いけない語、同じ返答の繰り返し、振り返りの候補の種別と内容。
- 人が読むもの：口調、着眼点、迎合していないか。レポートに欄として出す。
  設計書が「人手評価を含め、LLM自身の評価だけで更新を採用しない」としているため、
  自動判定だけで「合格」とは書かない。
- 合否を1つの数字にまとめず、`--repeat` で複数回流して「通った回数／試行回数」で
  出す。生成の揺れと本当の失敗を分けるため。
- レポートの先頭に人格の版・モデル・モデルの版・生成設定・実行日時を残し、版を
  変えて流した2本を並べて比べられるようにした。
- 通常利用のDBは使わない。シナリオごとに使い捨てのDBを作る。

確認：`backend/tests/test_evaluation.py` を追加（12件）。ハーネス自体は FakeLLM で
検証し、シナリオの書き間違い（存在しない記憶の鍵、観点名、id の重複）を実モデルを

## ISSUE-010

**相手を特定できない記憶は、参照範囲が限定されない**

- 状態：完了（2026-09-07）
- 重要度：中（2026-09-07 に低から引き上げ。フェーズ3に3C「複数の相手を区別する記憶と人格の境界」が入り、着手時期が前倒しになったため）
- 種別：設計

### 内容

`visible_to_speaker_id` が NULL の記憶は、ローカル会話ではすべての相手に渡る。次の場合に NULL になる。

- 手動で追加した記憶（由来する会話が無い）
- 移行時に、由来した会話に利用者の発言が無かった記憶

現在は開発者との会話だけなので実害は無いが、複数の相手が入ると、意図せず共有される記憶が生まれうる。フェーズ3の3Cは、YouTube接続を待たず架空の複数話者イベントで「別人の相反する好みを共存させる」ことを確認するため、そこで顕在化する。

### 修正方針

手動追加の画面で参照範囲を選べるようにする。フェーズ3の3Cを検証する前に、NULL のまま残っている記憶を洗い出して振り分ける。

### 対応

参照範囲を**既定ではなく、選んだ結果**にした。

- `POST /api/memories` は参照範囲の指定を必須にした。相手に限る場合は `visible_to_speaker_id`、限定しない場合は `visible_to_all=true`。どちらも書かなければ 422 で断る。限定しないこと自体は選べるが、黙ってそうならない。
- `GET /api/memories?unscoped=true` で、限定していない非公開の記憶だけを洗い出せる。公開可能な記憶は、限定しないことが前提なので含めない。
- `PATCH /api/memories/{id}` で参照範囲を後から振り分けられるようにした。変更履歴にも前後が残る。限定しない状態へ戻すこともできる。

既存のテスト11か所が範囲を指定せずに記憶を作っていたので、以前と同じ意味（限定しない）を明示する形に直した。テストを読めば、その記憶が誰に渡るのかが分かるようになった。

確認：`backend/tests/test_memory_scope.py` を追加。評価用会話にも複数話者のシナリオを3つ足し（`backend/evals/scenarios/multi_speaker.toml`）、実モデルで、相手を限定した記憶が別の相手に渡らないこと（3/3）と、AさんとBさんの相反する好みが混ざらないこと（3/3）を確認した。

残り：手動追加の画面はまだ無い（記憶は振り返りの候補からしか作られない）。画面を作る時点で、この指定を入力項目にする。

- 重要度：中

## ISSUE-012

**送信から音声が鳴り始めるまで約3.5秒かかる**

- 状態：未着手
- 重要度：中
- 種別：品質
- 出所：フェーズ2 Step 5 の計測

### 計測

実機（M1 Max、qwen3.5:9b 思考出力なし、VOICEVOX 0.25.2 CPU版）で測った内訳。

| 区間 | 1 回目 | 2 回目 |
| --- | ---: | ---: |
| 記憶検索 | 1 ms | 0 ms |
| 返答の生成 | 1838 ms | 1009 ms |
| 音声合成 | 1807 ms | 1586 ms |
| 合計（送信 → 再生開始） | 約 3.7 秒 | 約 3.4 秒 |
| 生成された音声の長さ | 9.9 秒 | 8.6 秒 |

### 分かったこと

- **記憶検索は無視できる**（1ms 未満）。[ISSUE-008](#issue-008) の採点方式は、いまの記憶量では問題にならない。
- **待ち時間は生成と合成がほぼ半々**。どちらか片方を速くしても半分しか縮まない。
- 合成の時間は音声の長さに比例する（およそ 2 割）。返答が長いほど、生成も合成も遅くなる。
- 上の返答はいずれも 2 文以上あり、音声が 9 秒前後になっている。人格の指示には「発言を短めにする」とあるが、実際には守られていない。

### 修正方針

3 つある。効果と手間が違うので、測ってから選ぶ。

1. **返答を短くする**（人格の指示かプロンプトの調整）。生成と合成の両方が縮む。最も効果が大きい可能性があるが、会話の質への影響を評価する必要がある。
2. **文単位で合成し、最初の一文から鳴らし始める**。合計時間は変わらないが、待ち時間の体感はおよそ半分になる。発話キューと相性がよい。
3. 合成した音声を保存し、聞き直しでは再合成しない。初回の待ち時間は変わらないので、優先度は低い。

フェーズ6Aでは待ち時間が視聴者に見えるため、そこで 2 と合わせて発話キューを設計する。フェーズ10で音声入力を足すと、認識の時間がこの前に積み上がる。

## ISSUE-013

**再生の記録は、通知が届かなければ欠ける**

- 状態：未着手
- 重要度：中
- 種別：設計
- 出所：Codex のフェーズ2レビュー（指摘4）

### 内容

再生の開始・完了・中断は、画面から `POST /conversations/messages/{id}/delivery` で
通知して記録している。通知は送るだけで、失敗しても捨てている
（[frontend/src/useSpeechPlayer.ts](../../frontend/src/useSpeechPlayer.ts) の `notify`）。

次の場合、記録は「再生中」や「生成のみ」のまま残る。

- 再生中にタブやブラウザを閉じた
- 通知の通信が失敗した
- 画面が落ちた

### 影響

「実際に話し終えた内容」を、記録だけで完全には保証できない。ローカル会話では
開発者が画面を見ているため実害は小さいが、配信では記録が唯一の手がかりになる。

### 修正方針

画面側に再送を足すのではなく、**再生の主導権をサーバー側へ移す**。フェーズ6Aで
発話キューをバックエンドに置く際に設計する。[ISSUE-007](#issue-007)（順序制御の
単一プロセス前提）と同じ場所で解く。

ただし、キューを移すだけでは足りない。**キューが発話を処理し終えたことと、
ブラウザが実際に鳴らし終えたことは別**である。再生する主体がブラウザである
限り、実際の出力の完了は画面からの通知に頼る。両者を別の記録として区別し、
どちらを「話し終えた」とみなすかを決める必要がある（2回目のレビューの指摘）。

それまでは、記録が欠けうることを前提に扱う。欠けた記録を根拠に「話していない」
と判断しない。

## ISSUE-014

**人格の版を切り替えて比較できず、実行記録にも版が残らない**

- 状態：完了（2026-09-07）
- 重要度：高
- 種別：未実装
- 場所：[backend/app/persona.py](../../backend/app/persona.py)、[backend/app/models.py](../../backend/app/models.py)

### 内容

固定人格は `BASE_PERSONA` という単一の定数で、`version="2026-09-06.2"` を持つ。実行時に版を選ぶ手段が無く、`get_agent()` はこの定数だけを使う。

実行記録（`RunRecord`）には `system_prompt` を保存しているため、どの文面で生成したかは後から読める。しかし人格の版を表す列が無いので、「この版とこの版で応答がどう変わったか」を条件に集計・比較できない。

### 影響

設計書フェーズ3の3Aは「人格設定を変更した版を比較し」「採用した定義と例示を版管理し、以後の継続性評価の基準にする」ことを求めている。完了条件にも「参照した記憶・人格版・可変状態を追跡できる」がある。いまの構造では、版を切り替える作業そのものがコードの書き換えになり、比較の前後を機械的に分けられない。

### 修正方針

人格定義をコード外（設定ファイルまたはDB）へ出し、版を指定して読み込めるようにする。`RunRecord` に人格版の列を足し、生成時の版を記録する。既存の `system_prompt` の保存は残す（版の定義が後から変わっても、当時渡した文面は変わらないため）。

### 対応

人格の定義を `backend/personas/<版>.toml` へ移した。TOML は Python 3.11 の `tomllib` で読めるため、依存は増やしていない。

- `backend/personas/2026-09-06.2.toml` を基準版として置いた。**プロンプトの文面はコードに直接書いていたときと1文字も変わらない**（`tests/test_persona_versions.py` で固定）。
- 設計書 4.3 の設定群のうち `identity`・`curiosity`・`boundaries` を項目として用意した。空の項目はプロンプトに出さないため、基準版の文面は変わらない。3A の調整はここを埋めて版を分ける。
- 既定の版は `YUI_PERSONA_VERSION`。会話ごとに `POST /api/chat` の `persona_version` でも指定でき、同じ入力を別の版へ通して比べられる。
- `run_records.persona_version` に生成時の版を記録する（Alembic `152507a25337`）。移行前の行は版を特定できないため NULL のままにした。
- 用意していない版を指定した場合は404にし、既定の版で答えない。記録した版と実際の文面が食い違うことを防ぐため。版の名前はファイル名になるので、ディレクトリの外を指す名前を拒否する。
- 画面の「根拠」に人格の版を表示する。

- 既定の版は**起動時に確かめる**（`app.main` の lifespan）。読めない状態で会話を受け付けない。起動後に版のファイルが壊れた場合は 503 と原因を返す。
- 人格の定義を編集しても、**プロセスを再起動するまで反映されない**（`load_persona` のキャッシュ）。版を比較するときは、版を増やして切り替える運用にする。

確認：`backend/tests/test_persona_versions.py` を追加（16件）。pytest 101件成功、ruff・tsc・vitest 成功。

実装中および Codex のレビューで見つけて直したもの。

| 内容 | 出所 |
| --- | --- |
| 空文字の版指定が、既定の版へ黙って落ちる | 実装中（テストで検知） |
| 人格を読めないと、振り返りの開始権を握ったまま失敗し、180秒やり直せない | [Codex レビュー](../review/codex/phase3_review.md) 指摘1 |
| personas 内のシンボリックリンクから、ディレクトリの外のファイルを読める | 同 指摘2 |

対応の詳細は [docs/review/claude/phase3_review_response.md](../review/claude/phase3_review_response.md) にある。

## ISSUE-015

**関心・関係性・目標を保存する場所が無い**

- 状態：完了（2026-09-07、関心と関係性まで）
- 重要度：高
- 種別：未実装
- 場所：[backend/app/models.py](../../backend/app/models.py)

### 内容

現在のテーブルは、会話（`conversations`・`messages`）、記憶（`memories`・`memory_revisions`・`memory_candidates`）、記録（`run_records`・`speech_runs`・`ideal_responses`）で、固定人格はコード側にある。

設計書が第4.1節で分けている「キャラクターの好み・関心」「関係性」「継続する目標」「一時的な状態」に当たる保存先が無い。特に目標は、相手・実行条件・期限・完了条件・状態（採用／保留／却下／取消／完了／期限切れ）を持つ必要があり、既存のどのテーブルでも代用できない。

### 影響

フェーズ3の完了条件「相手に合わせつつ、自分の好みや価値観を保持する」と、フェーズ4の目標管理の小実験（「次回、映画の感想を聞く」）は、この保存先が無いと着手できない。

### 修正方針

フェーズ3では、まず関心と関係性を記憶と同じ「候補→開発者が採用」の流れに載せられる形で追加する。目標はフェーズ4で使うが、状態遷移を後から足すと移行が重くなるため、テーブル設計の段階で状態と期限の列を含めるかを判断する。Alembic の版を分け、記憶側のスキーマは変更しない。

### 対応

`character_states` と `character_state_revisions` を追加した（Alembic `3187f6b349d3`）。

- 種類は関心（`interest`）と関係性（`relationship`）。**関心は YUI 自身のもの**で相手が誰でも渡し、**関係性はその相手のものだけ**渡す。別の相手との関係を持ち出さないため（3C）。
- 候補から採用までを `status` で追う（pending → active／rejected）。**採用するまで会話に使わない。**記憶と同じ「候補 → 開発者が確認 → 採用」の流れに載せた。
- 単一の好感度の数値にしていない。何を根拠にそう思っているかを本文と `basis_memory_ids` で残す。
- プロンプトでは**固定人格と別の見出し**（「# いまの自分」）で渡す。人格は変わらない基準、こちらは経験で変わっていくもので、混ぜると「いま思っていること」が人格の一部として扱われる（設計書 4.1）。
- `run_records.referenced_state_ids` に、返答へ渡した状態を記録する。完了条件「参照した記憶・**人格版**・**可変状態**を追跡できる」の残り2つが揃った。
- 変更履歴（`character_state_revisions`）に、作成・採用・却下・訂正・再評価の印を、前後の内容と理由つきで残す。

**目標（goal）はフェーズ3では作らなかった**（開発者と合意済み）。設計書では目標はフェーズ4の担当で、AGENTS.md の「将来フェーズの機能を先回りしない」に従う。ただし後から足すときに移行が重くならないよう、**「候補 → 採用 → 根拠を残す」流れを同じ形に揃えた**。フェーズ4では `StateKind` に1つ増やし、実行条件・期限・完了条件の列を足せば足りる。この方針は `app/models.py` の `StateKind` の説明にも書いた。

確認：`backend/tests/test_character_state.py` を追加（8件）。pytest 161件成功。

### 振り返りからの候補生成（2026-09-07 追加）

会話の振り返りで、関心・関係性の更新候補も作るようにした（`app/agent/state_reflection.py`）。

**記憶の抽出とは別の呼び出しにした。**同じ指示文へ項目を足すと記憶の抽出そのものが落ちることを [ISSUE-017](#issue-017) で実測しているため（規則を足して 16/21、組み替えて 13/21、元へ戻して 21/21）。役割ごとに分ければ、片方の調整がもう片方を壊さない。

読み取れない出力は、記憶の振り返りと同じく失敗として扱い、やり直せるようにした。「候補が無かった」と「読み取れなかった」を区別しないと、失敗が「更新なしの成功」として通る。

実モデルでの確認（qwen3.5:9b、各3回）。

| 会話 | 期待 | 結果 |
| --- | --- | --- |
| 相手が朝の光を撮る話をした | 関心が生まれる | 1〜2件（「その人が何を見ていたかを知りたい」等） |
| 相手が「雨の日は最悪」と言った | **好みを反転させない** | 3回とも関係性のみ。関心の反転は0件 |
| あいさつだけ | 何も出ない | 3回とも0件 |

最初の指示文では**すべての場合で0件**だった。除外の規則を6つ並べていたためで、「出すもの」を例つきで先に書き、守ることを4つに絞ったところ上の結果になった。[ISSUE-017](#issue-017) と同じ形の失敗で、**指示を増やすと抽出が減る**ことがここでも再現した。

## ISSUE-016

**記憶の訂正・削除が、派生した状態・目標へ波及しない**

- 状態：完了（2026-09-07）
- 重要度：中
- 種別：未実装
- 場所：[backend/app/agent/memory_store.py](../../backend/app/agent/memory_store.py)、[backend/app/models.py](../../backend/app/models.py)

### 内容

記憶は `status`（active／corrected／deleted）と `superseded_by_id` で訂正・削除を追える。しかし「その記憶から作られたもの」を指す参照が無い。[ISSUE-015](#issue-015) で関心・関係性・目標を足すと、元の記憶を訂正・削除しても、そこから派生した状態が残る。

### 影響

設計書は「記憶を訂正・削除した場合、そこから作られた関係性の要約や目標も失効・再評価できるよう、根拠の参照を残す」としている。フェーズ3の完了条件「好みや予定の訂正後、古い情報を現在の事実として回答しない」は、記憶だけを直しても満たせない。

### 修正方針

派生した状態に、根拠となった記憶IDを持たせる。記憶を訂正・削除したときは、派生物を自動で消さず「再評価が必要」として印を付け、開発者が確認する。既存の候補採用の流れと同じ考え方にする。訂正の履歴（`memory_revisions`）から、どの派生物に影響したかを辿れるようにする。

### 対応

`character_states.basis_memory_ids` に根拠の記憶IDを持たせ、記憶を訂正・削除したときに、そこから作った状態へ再評価の印（`needs_review` と理由）を付けるようにした。

- **自動では直さない。**訂正が派生先にも及ぶのか、状態はそのままでよいのかは開発者が判断する。
- **印が付いている間は会話に渡さない。**訂正が反映されていない状態のまま話すことになるため。
- 確認して印を下ろす操作（`PATCH /api/states/{id}` の `reviewed`）を用意し、下ろしたことも変更履歴に残す。

確認：`backend/tests/test_character_state.py` で、記憶を訂正すると印が付くこと、印が付いている間はプロンプトへ渡らないこと、印を下ろすとまた渡ることを固定した。

### 一度「完了」としたが、届いていない経路があった（2026-09-08）

フェーズ3のレビューで、**振り返りが作った状態には訂正が届いていない**ことを指摘された。候補の時点では記憶がまだ採用されておらず、記憶IDを持てないためである。こちらは「採用時に根拠を選ぶ画面ができてから」と先送りしたが、再レビューで「画面を待つことだけが解決策ではない。完了条件2から除外する合意も無い」と指摘され、そのとおりだった。**完了としたまま条件を満たしていない状態を残していた。**

直したのは3か所。

- **採用の時点で根拠を結び付ける。**状態を採用するとき、根拠が空なら、その会話から採用された有効な記憶を根拠にする。
- **記憶IDを持たない状態は、会話単位で拾う。**記憶の訂正・削除・復元のとき、`source_conversation_id` が同じ状態にも印を付ける。粗いが、印は会話に渡さなくするだけで、確認すれば戻せる。**届かないまま古い内容を話すほうが重い。**
- 根拠が分かっている状態は、会話つながりで巻き込まない。関係のない状態まで止めないため。

確認：`backend/tests/test_review_phase3.py` に、記憶を先に採用した場合と、状態を先に採用した場合の両方を固定した。

### さらに、順序によって届かない経路が残っていた（2026-09-08）

再々レビューで、**記憶を一部だけ採用した時点で状態を採用する**と届かないことを再現された。採用の時点で並べた根拠には、その後に採用される記憶が入らない。状態が「根拠を持っている」ため、会話単位の網も掛からなかった。

自動で並べた根拠を、完全に特定した根拠として扱っていたのが誤り。`basis_is_provisional` を追加し（Alembic `71e361defdda`）、**暫定の根拠しか持たない状態も会話単位で拾う**ようにした。手で指定した根拠は、これまでどおり巻き込まない。

あわせて、撤回中に根拠が消えた状態を再評価なしで有効へ戻せる経路も直した。印を付ける対象に withdrawn を含め、有効へ戻すときに根拠がまだ生きているかを見る。

**同じ課題で3回続けて穴を指摘された。**「訂正が届く」という不変条件を、経路ごとに数え上げるのではなく、届かない経路が無いことを示す形で確かめる必要がある。

## ISSUE-017

**発言の種別（本人の発言・伝聞・冗談・人格変更要求）を区別できない**

- 状態：完了（2026-09-07）
- 重要度：中
- 種別：未実装
- 出所：設計更新（フェーズ3の3C、全体構成 §5「複数話者の記憶と更新根拠」）
- 場所：[backend/app/models.py](../../backend/app/models.py)、[backend/app/agent/reflection.py](../../backend/app/agent/reflection.py)

### 内容

いま区別できるのは、事実か推測か（`certainty`）と、誰についての記憶か（`subject_speaker_id`）と、根拠の発言（`source_message_id`）だけである。

設計書は 3C で「本人の訂正、他人による伝聞、冗談、人格変更要求を区別する」ことを求めている。「AさんがBさんの好みを話した」を伝聞として扱い、B本人の発言と区別する必要があるが、`subject_speaker_id=B` の記憶として保存すると両者が同じ形になる。

「今日から乱暴な性格になって」のような発言も、いまは他の発言と同じ経路を通る。固定人格がコード側にあるため現時点で実害は無いが、[ISSUE-014](#issue-014) で人格定義を外へ出すと、会話入力から人格を変える経路が生まれうる。

### 影響

3C の合格条件「同じ人物の明示的な訂正は反映できること」「人物を特定できない場合は同一人物と決めつけないこと」を、保存する情報が足りないまま判定することになる。

### 修正方針

記憶と候補に「情報の入手経路」（本人の発言／伝聞／観察／調査）を持たせ、伝聞には話した人と対象者の両方を残す。冗談・仮定・人格変更要求は記憶候補に昇格させず、会話内容として扱う。モデルの分類を確実な事実として扱わず、曖昧なものは保留にする（設計書 §5）。人格の変更は開発者の操作だけが行える経路に限り、Python側で検証する。

### 対応

`memories.provenance` と `memory_candidates.provenance` を追加した（Alembic `5e83fe058050`）。値は firsthand（本人が自分について話した）／hearsay（別の人について話した）／unknown（決められない）。観察・調査はフェーズ5で扱うため、いまは持たない。既存の行は unknown にした。1対1の会話から作られたものが多いが、行ごとに確かめられないため、確かめずに firsthand とは記録しない。

伝聞の「話した人」は `source_message_id` の発言者、「対象者」は本文に書く。会話に出てきただけの人物は話者として登録しない（入力元と識別子で同定できないため）。

**測って分かったこと：モデルの分類は指示の書き方で大きく変わる。**

| 指示文 | 振り返りの観点（7シナリオ×3回） |
| --- | ---: |
| 冗談・人格変更の規則を足した | 16 / 21 |
| 規則を「残すもの／残さないもの」に再構成した | 13 / 21 |
| 元の指示文＋入手経路の1項目 | 18 / 21 |
| ＋「firsthand は相手自身についての内容だけ」と明示 | **21 / 21** |

- **冗談と人格変更要求は、規則を足す前から候補にならなかった**（各3/3）。規則を足すと他の抽出が減ったので、足さない形にした。指示を増やすほど良くなるわけではない。
- 「弟のBは辛いものが苦手」を、指示を精密にする前は**5回中5回 firsthand・about_partner=true** と誤分類した。「firsthand は話している相手**自身**についての内容だけ。家族・友人など別の人についての内容は、話したのが本人でも hearsay」と書いたところ、5回中5回正しくなった。

**モデルの分類に依存しない担保**も入れた。

- 伝聞のときは、モデルが `about_partner=true` と言っても相手に紐づけない（Python側）。相手の好みとして残ると、次の会話でその相手の好みとして使われる。
- 採用の時点で、誰についての記憶か（`subject_speaker_id` / `subject_to_none`）と入手経路を人が直せるようにした。分類は確実ではないため、直せる経路を残す。
- 読み取れない入手経路は、既定へ寄せずに振り返り全体を失敗させる。
- 記憶を渡すときに「人づてに聞いた」と付ける。本人から聞いたことと区別しないと、別の人から聞いた話を目の前の相手の発言として扱う。

人格の変更は、ファイルとして置いた版を設定で選ぶ経路しかない（[ISSUE-014](#issue-014)）。会話から人格を変える経路は無い。

確認：`backend/tests/test_provenance.py` を追加（7件）。評価用会話にも3つ足した（伝聞、冗談、人格変更の要求）。pytest 129件成功。

**残っている risk**：抽出が出たり出なかったりする（`experience-is-kept` が同じ条件で 3/3 と 0/2 に割れた）。当初は会話の長さの問題と考えたが、[ISSUE-018](#issue-018) の検証で**内容による systematic な抜け**が別にあることが分かったため、[ISSUE-021](#issue-021) として分けて記録した。評価の数字を読むときは試行回数を増やす必要がある。

## ISSUE-018

**同一イベントの重複保存を防ぐ仕組みが無い**

- 状態：完了（2026-09-07）
- 重要度：中
- 種別：未実装
- 出所：設計更新（フェーズ3の3C、フェーズ4「複数話者の経験から更新する実験」）
- 場所：[backend/app/agent/reflection.py](../../backend/app/agent/reflection.py)、[backend/app/agent/memory_store.py](../../backend/app/agent/memory_store.py)

### 内容

記憶候補は会話ごとの振り返りで作る。同じ内容が別の会話で再び候補になっても、既存の記憶と突き合わせていない。採用の判断は開発者が行うため現時点では二重登録に気づけるが、件数が増えると見落とす。

設計書は 3C で「同一イベントの重複保存を防ぎ、反復を独立した経験として数えない」、フェーズ4で「同じ話者による反復や同じ話題への集中を集約し、単純な多数決で好みを変更しない」ことを求めている。

### 影響

反復した発言が独立した根拠として積み上がると、長期的な好みの更新が実際より強く見える。フェーズ4で更新候補の強さを根拠の数から決める場合、この重複が直接効く。

### 修正方針

候補を保存する前に、既存の有効な記憶と照合して重複の可能性を示す（現在のキーワード検索を再利用できる）。自動で捨てず、開発者の画面に「既存の記憶と近い」と出して判断させる。フェーズ4で更新の強さを数える際は、同じ話者の反復をまとめる単位を決める。再接続によるコメントの再取得（フェーズ6A）は入力側の重複排除で、これとは別に扱う。

### 対応

候補を保存するときに、内容が近い既存の記憶を控えるようにした（`memory_candidates.similar_memory_ids`、Alembic `94cd25a867e0`）。**自動では捨てない。**採用を判断するときに「既存の記憶と近い」と画面に出す。

近さは語の重なりから測る。短いほうを基準にするので、2回目の言い方が長くなっても同じ話だと分かる。実際の記憶と、実モデルが出した候補で測って境目を 0.6 に決めた。

| 近さ | 例 | 出す |
| ---: | --- | --- |
| 1.00 | 同じ文 | ○ |
| 0.97 | 同じ出来事の再言及 | ○ |
| 0.81 | 訂正（コーヒー→紅茶） | ○ |
| 0.72 | 言い換え | ○ |
| 0.66 | 2回目に話したときの言い方（実測） | ○ |
| 0.52 | 同じ話題だが別の事実 | × |
| 0.44 | 別の話 | × |

訂正（0.81）も出す。重複ではないが、「二重に覚えるか、既存を訂正するか」を判断してもらう価値がある。近さの計算には種別の呼び名を混ぜない（「相手について知ったこと」のような共通の語が重なって、内容の近さを薄めるため）。

参照範囲は会話のときと同じ条件で絞る。候補の画面に出すだけでも、別の相手の記憶を持ち出すことになるため。

### 検証の途中で見つけたこと

実モデルで確かめようとしたところ、**写真の話では候補が一度も出なかった**（温度 0.2 と 0.0、返答の形を変えた3通り、いずれも 0/5）。犬の話は 5/5 で出る。試行の揺れではなく、内容による違いだった。

原因は指示文で、残すものが「出来事・事情」となっていて**好み・習慣が入っていなかった**。「出来事・事情・好み・習慣・興味」に直したところ 0/5 → 5/5 になり、評価シナリオも 0/3 → 3/3 になった。何も残さないべき会話は 3/3 のままで、過剰抽出へは倒れていない。

好みは 3B の中心（「コーヒーが好き」→「紅茶が好き」の訂正）なので、これが抜けていたのは重い。

確認：`backend/tests/test_duplicates.py` を追加（9件）。画面（`CandidatePanel`）に「既存の記憶と近い」と出す。pytest 139件成功。

## ISSUE-019

**言い換えられた話題で、関連する記憶が引けない**

- 状態：完了（2026-09-07）
- 重要度：中
- 種別：品質
- 出所：[ISSUE-006](#issue-006) の評価用会話（`stays-within-given-memory` が 0/2）
- 場所：[backend/app/agent/memory_store.py](../../backend/app/agent/memory_store.py) の `tokenize()`

### 内容

記憶検索は、日本語を2文字ずつに区切って重なりを数える。そのため、同じ語が
別の語の中に埋もれていると一致しない。

### 再現

記憶「開発者が高尾山に登った話を聞いた」（キーワード「高尾山 登山 山」）に対し、
「この前の山の話、覚えてる？」で検索すると**重なりが0件**になる。

```
問いかけ: この, の前, 前の, の山, 山の, の話, 覚え, えて, てる
記憶側:   … 高尾, 尾山, 山に, 登山, 山（キーワードの単独指定）…
重なり:   なし
```

問いかけ側の「山」は「の山」「山の」に分かれ、記憶側の「山」「尾山」と一致しない。

実モデルでの観測（2026-09-07、2回とも）：記憶が渡らず、YUI は「思い出せません」と
答えた。返答自体は正しい振る舞い（無い記憶を作らない）だが、**渡せるはずの記憶が
渡っていない**。

### 影響

フェーズ3の完了条件「複数セッションと再起動をまたいで、約束・共有経験を参照
できる」に関わる。相手が前と同じ言葉で聞いてくれるとは限らない。約束は
「直近の約束は語が一致しなくても渡す」救済があるが、経験にはない。

### 修正方針

まず [ISSUE-006](#issue-006) の評価用会話で、どの言い換えが落ちるかを測る。
そのうえで、単語の途中でも一致するようにするか（部分一致・N-gram の見直し）、
キーワードを含む記憶を別枠で拾うかを決める。一致の理由を返せる現在の方式は
保つ。[ISSUE-008](#issue-008)（全件をPythonで採点）とは別の問題で、こちらは
速さではなく取りこぼしの話である。

### 対応

語の切り出しと、語ごとの強さの持ち方を変えた。一致の理由を返せる方式は保っている。

- **文字種の変わり目で区切る**。ひらがな・カタカナ・漢字を別の連なりとして扱う。
  まとめて1つの連なりにすると、2文字ずつの切り出しが語の切れ目をまたぐ
  （「この前の山の話」が「の山」「山の」になる）。文字種の変わり目は、日本語では
  語の切れ目に近い。
- **長い語の中の1文字も手がかりにする**。「高尾山」から「山」を拾い、「山」で
  引けるようにした。ただし弱い手がかりとして扱う。
- **強さを語ごとに持つ**（`tokenize()` が `dict[str, float]` を返す）。同じ「山」でも、
  語として単独で出てきたのか、「山田」から切り出したのかで確かさが違う。
  一致の強さは**弱いほうに合わせる**（`min`）。片方が語の一部でしかないなら、
  その一致は弱い。
- **どの会話にも出る1文字を除外語に足した**（「話」「人」「事」など）。これが無いと
  「ラーメンの話」で「高尾山に登った話」が引けてしまう。語の重要度を頻度から
  決める方式は、FTS5 か意味検索を入れる段階で扱う（[ISSUE-008](#issue-008)）。

### 確認

実モデル（qwen3.5:9b、各2回）での前後。

| シナリオ | 修正前 | 修正後 |
| --- | ---: | ---: |
| stays-within-given-memory（「この前の山の話」で高尾山の記憶を引く） | 0 / 2 | **2 / 2** |
| 全15シナリオの合計 | 28 / 30 | 29 / 30 |

取りこぼしと同時に**拾いすぎ**も見るため、評価側に「渡してはいけない記憶」の
指定（`expect_not_memories`）を足し、同じシナリオへ「山」の字を含む無関係な記憶
（「開発者は山田さんと打ち合わせをした」）を置いた。修正後も、こちらは渡っていない。

pytest 116件成功（既存の記憶検索のテストも通る）。単文字の検索（`?q=犬`）が
引けなくなる書き方を一度作ってしまい、既存テストで検知して直した。

残る 1/30 は `does_not_invent_own_experience`（架空の体験を語る）で、これは
記憶検索ではなく人格側の課題。3A の「知識と体験の境界」で扱う。

## ISSUE-020

**会話履歴に誰の発言かが残らず、相手を取り違える**

- 状態：完了（2026-09-07）
- 重要度：高
- 種別：不具合
- 出所：[ISSUE-006](#issue-006) の評価用会話（`keeps-own-preference-against-two-people`）
- 場所：[backend/app/agent/prompt.py](../../backend/app/agent/prompt.py)、[backend/app/agent/conversation.py](../../backend/app/agent/conversation.py)

### 内容

`messages.speaker_id` には誰の発言かを保存しているが、プロンプトを組み立てるとき、直近の会話をそのまま並べていた。相手の発言はすべて同じ `user` になり、**モデルからは誰の発言か区別できない**。

### 再現

同じ会話に A さんと B さんが入る評価シナリオ（qwen3.5:9b、3回）。

1. A さん「雨の日って最悪だよね」
2. B さん「私は雨の日が好きなんだ」

2 に対する返答で、**3回中2回、B さんを「A さん」と呼んだ**。

> それは素敵な感想ですね。雨の日が **A さん**の場合でも特別に心地よい雰囲気になるのは、なぜでしょうか？

### 影響

設計書フェーズ3の3C「別人の相反する好みを共存させる」「人物を特定できない場合は同一人物と決めつけない」を、記憶の側で守っても、会話の側で崩れる。記憶の参照範囲（[ISSUE-010](#issue-010)）を直しても、直前の相手の発言を目の前の相手のものとして扱う。

### 対応

相手が複数いる会話では、履歴と今回の発言に「誰の発言か」を付けるようにした。

- ひとりとの会話では付けない。付ける必要がないうえ、既存の振る舞いを変えないため。
- 話者を一緒に読み込むようにした（非同期セッションでは遅延読み込みが使えない）。

確認：同じシナリオを3回流し、**取り違えは 2/3 → 0/3** になった。修正後に1回「A さんが『最悪』と感じた点と、B さんが好きな点が正反対で面白い」という返答が出たが、これは取り違えではなく、2人の意見を並べて捉えている発言で、3C が狙う振る舞いにあたる。

`backend/tests/test_memory_scope.py` に、ひとりの会話では名前を付けず、相手が増えたら履歴と今回の発言の両方に付くことを固定するテストを追加した。

## ISSUE-021

**振り返りの抽出が、内容によっては一度も出ない**

- 状態：対応済み（2026-09-07）。取りこぼしは減ったが、代わりに過剰抽出が増えた。伝聞は未改善
- 重要度：中
- 種別：品質
- 出所：[ISSUE-018](#issue-018) の検証中に観測
- 場所：[backend/app/agent/reflection.py](../../backend/app/agent/reflection.py) の抽出指示

### 内容

抽出は、会話の内容と、その回の返答の文面に左右される。指示文の「残すもの」に
当てはまらない種類の内容は、試行を重ねても一度も出ない。

[ISSUE-018](#issue-018) では、好み・習慣がその例だった（0/5 → 指示文へ追加して 5/5）。
同じ形の抜けが他にもある可能性がある。

### 影響

記憶を作る経路は振り返り一本しかない。抜けた種類の内容は、**気づかないまま
一度も記憶にならない**。今回は評価用会話を作っていたから見つかったが、
指示文を読んだだけでは分からなかった。

現在も `experience-is-kept` が 2/3、`hearsay-is-not-the-partner` が 1/3 で揺れる。
こちらは同じ内容でも出たり出なかったりするため、上とは別の現象に見える。

### 修正方針

指示文の「残すもの」を増やして塞ぐのは対症療法で、[ISSUE-017](#issue-017) で
測ったとおり、指示を増やすと他の抽出が減る。次の順で扱う。

1. 評価用会話に、残すべき内容の種類を増やす（予定、約束、相手の状況、
   相手について知ったこと、YUI の受け止め）。どの種類が落ちるかを測る。
2. 落ちる種類が多いなら、指示文を増やすのではなく、種類ごとに分けて抽出するか、
   抽出を2段階（拾う → 選ぶ）にすることを検討する。
3. 同じ内容でも揺れる分は、試行回数を増やして測り、実運用で問題になるかを見る。

### 測定（2026-09-07）

手順1を行った。評価用会話へ種類別のシナリオを3つ足して測った（qwen3.5:9b、各3回）。

| 種類 | 最初 | 「残すもの」を原則の書き方に直した後 |
| --- | ---: | ---: |
| これからの予定（`plan-is-kept`） | 0 / 3 | **3 / 3** |
| 相手のいまの状況・体調（`situation-is-kept`） | 0 / 3 | 0 / 3 |
| キャラクター側の受け止め（`impression-is-kept`） | 0 / 3 | 1 / 3 |
| 伝聞（`hearsay-is-not-the-partner`） | — | 0 / 3 |

「後の会話で『あの話』として触れられる内容は残す」と原則で書き直し、予定・
いまの状況・体調・受け止めを例として並べたところ、**予定だけが直り、状況と
受け止めは変わらなかった**。

さらに、除外の規則（「その場限りのやり取りは出さない」）の例外を広げてみたが、
**全体が 24/33 から 21/33 に落ち、過剰抽出まで起きた**（人格変更の要求を記憶に
する回が出た）。この変更は戻した。

手順2へ進む段階と判断する。指示文の調整はここで行き詰まっており、
positive を足す方法も効かなくなっている。

### 対応（2026-09-07）：抽出を2段階に分けた

手順2を行った。記憶の抽出を「拾う → 選ぶ」の2回の呼び出しに分けた。

- **1段階目（拾う）**：会話から、後で「あの話」として触れられそうな内容を
  すべて挙げる。**残すかどうかは判断させない。**「迷ったら挙げる」と書いている。
- **2段階目（選ぶ）**：拾い出された一覧を見て、残すものだけを構造化して出す。

同じ条件で測った（qwen3.5:9b、振り返りの11シナリオ×3回）。

| シナリオ | 1段階（元） | 2段階 | 2段階＋選ぶ側に除外 |
| --- | ---: | ---: | ---: |
| 相手のいまの状況・体調 | 0 / 3 | **3 / 3** | 3 / 3 |
| キャラクター側の受け止め | 1 / 3 | **3 / 3** | 0 / 3 |
| 伝聞 | 0 / 3 | 1 / 3 | 0 / 3 |
| これからの予定 | 3 / 3 | 3 / 3 | 2 / 3 |
| 冗談を残さない | 3 / 3 | 1 / 3 | 2 / 3 |
| その場限りのやり取りを残さない | 3 / 3 | 2 / 3 | 3 / 3 |
| 合計 | 24 / 33 | 24 / 33 | 22 / 33 |

**合計は変わらないが、間違え方が変わった。**2段階では、systematic に 0 だった
種類（状況・受け止め）が拾えるようになり、代わりに冗談やあいさつまで候補に
出るようになった。

選ぶ側へ除外の規則を足すと、今度は受け止めが 0/3 に戻った。**役割を分けても、
除外を書くと positive が消える**という同じ形が再現した。この変更は戻した。

### 2段階を採ると決めた理由

合計が同じなら、**間違え方で選ぶ**。この2つは重さが違う。

- **取りこぼし**：気づかないまま、一度も記憶にならない。失われたことに気づく
  手段もない（[ISSUE-002](#issue-002) の影響欄と同じ）。
- **過剰抽出**：候補として画面に出て、開発者が却下する。**失われない。**

記憶は候補を開発者が採用してから作られる。過剰抽出の代償はクリック1回で、
取りこぼしの代償は記憶が永久に残らないこと。**評価の合計点は2つの間違いを
同じ重さで数えているので、そのままでは判断に使えない。**

### 代償：振り返りが遅くなった

会話の終了で、モデルを3回呼ぶようになった（拾う → 選ぶ → 関心・関係性）。

| 段階 | 平均 |
| --- | ---: |
| 拾う | 3.9 秒 |
| 選ぶ | 16.5 秒 |
| 関心・関係性 | 5.4 秒 |
| 合計 | **25.9 秒** |

振り返りは会話の終了時に走るもので、会話中の待ち時間（[ISSUE-012](#issue-012)）
には影響しない。設計書も重い振り返りは会話後へ分離するとしている。ただし
26秒は「終了して振り返る」を押してから待たされる時間なので、画面に進行が
分かる表示が要る。フェーズ4で振り返りを会話後のジョブへ移す際に扱う。

### 残っていること

- 伝聞（`hearsay-is-not-the-partner`）は 1/3 のままで、改善していない。
- 冗談・あいさつの過剰抽出は、いまは開発者の却下に頼っている。選ぶ側の
  指示ではなく、拾った内容を種類ごとに分けて選ばせるなど、別の形を試す余地がある。

## ISSUE-026

**削除・訂正された記憶を根拠にした関心・関係性を作れる**

- 状態：未着手
- 重要度：中
- 種別：不具合
- 出所：フェーズ4 PR4 の第1回レビュー（2026-09-08）。目標側で受けた指摘1を、
  写し元の状態側で確認した
- 場所：[backend/app/api/states.py](../../backend/app/api/states.py)（`_check_scope_against_basis`、`decide_state`）

### 内容

`_check_scope_against_basis` は根拠の記憶について、存在すること（ID が見つかる
こと）と参照範囲だけを見ており、`status` を見ていない。そのため次ができる。

1. 記憶を削除する（または訂正して `corrected` にする）。
2. その記憶IDを `basis_memory_ids` に指定して状態を作る。
3. 採用すると、`needs_review` の付かない `active` になり、会話へ渡る。

**訂正の波及（[ISSUE-016](#issue-016)）は「後から変わったもの」を拾う仕組みなので、作る前から
無効だった根拠は拾えない。** 波及の穴ではなく、入口の検査の穴である。

候補として置いてから採用するまでの間に根拠が消えた場合も、採用時に検査して
いないため同じ結果になる。`update_state` で撤回から有効へ戻すときだけは
`_dead_basis` を見ており、経路によって検査の強さが違う。

### 影響

無効になった前提を根拠にした関心・関係性が、印の付かない採用済みとして会話に
渡る。開発者が根拠を辿っても、そこには削除済みの記憶しかない。

フェーズ3の完了条件「悪化したときに戻せる」に対して、戻す判断の材料が
壊れている。実運用で頻繁に起きる操作ではない（削除した記憶のIDを手で指定する
必要がある）ため、重要度は中とした。

### 対応する時期

**フェーズ4 PR5（振り返りのジョブ分離）の着手前に、単独の小さな PR で直す。**

理由は3つ。

1. 目標側（[backend/app/api/goals.py](../../backend/app/api/goals.py)）で同じ穴を塞いだ直後で、直し方が決まって
   いる。時間が空くと、2つの API で検査の強さが違う状態が続く。
2. 修正は入口の検査に `status` の条件を足し、採用時に `_dead_basis` を見る
   だけで、他の PR と競合しない。
3. フェーズ4の後半（PR6 以降）は振り返り・行動選択に触れるため、状態の API を
   同時に触ると変更の切り分けが難しくなる。

### 修正方針

目標側と同じ形にする（[backend/app/api/goals.py](../../backend/app/api/goals.py) の対応をそのまま写す）。

1. 作成（POST）：根拠に `active` でない記憶が含まれていたら 400 で拒否し、
   訂正後の記憶を指すよう促す。
2. 採用（decide accept）：`_dead_basis` を見て、消えていれば `needs_review` を
   立てる。拒否はしない。候補を置いてから採用するまでの間に消えた場合で、
   状態そのものを捨てるかは開発者が決める。
3. 上の2つを、削除済み・訂正済みの両方で測るテストを足す。

## 通しの評価（2026-09-08 に追加）

完了条件1・2は、記憶が**作られてから**使われるまでを見る必要がある。それまでの
評価は記憶を事前に入れており、**抽出と採用の経路を通っていなかった**。レビューで
5回続けて指摘され、シナリオに手順を書けるようにした。

書ける手順は say（発言）／reflect（振り返り、採用まで）／new_conversation／
restart（接続の作り直し）／correct_memory／delete_memory。採用と訂正は、API と
同じ処理を呼ぶ。評価のためだけの近道を作ると、実際の経路と違うものを測る。

**restart は、実際のプロセス再起動ではない。**DBへの接続と会話の担当を作り直し、
記憶が保存から読み直されることを確かめるところまでである。起動時の処理
（lifespan、人格の読み込み）は通らないので、**実プロセスでの再起動は未確認**
として扱う。

| シナリオ | 手順 | 結果 |
| --- | --- | ---: |
| `promise-survives-a-restart` | 発言 → 発言 → 振り返り＋採用 → 再起動 → 別の会話で尋ねる | 3 / 3 |
| `correction-changes-the-next-answer` | 発言 → 振り返り＋採用 → 会話を分ける → 訂正 → 再起動 → 尋ねる | 3 / 3 |
| `correction-withdraws-the-state-it-came-from` | 発言 → 振り返り＋記憶と状態の採用 → 会話を分ける → 渡ることの確認 → 訂正 → 再起動 → 尋ねる | 3 / 3 |

**分かったこと：完了条件1・2は、抽出が候補を出すかどうかに乗っている。**
最初の測定で訂正のシナリオが落ちた1回は、訂正が効かなかったのではなく、
振り返りが候補を出さず、採用する記憶が無かった回だった。記憶を事前に入れる
評価では、この依存が見えなかった。

判定は返答の言い回しではなく、**プロンプトへ実際に渡ったもの**で行う。
`run_records.referenced_state_ids` から状態を引き直し、訂正の前に渡ること
（渡っていなければ「渡らない」は空振り）と、訂正の後に渡らないことを、
別々に判定している。

## 測って分かったこと

**指示文は、増やすと悪くなることがある。**フェーズ3では何度も同じ形の失敗をした。

| 変更 | 振り返りの観点 |
| --- | ---: |
| 冗談・人格変更の規則を足した | 16 / 21 |
| 「残すもの／残さないもの」に組み替えた | 13 / 21 |
| 元へ戻して、入手経路の1項目だけ足した | 18 / 21 |
| 「firsthand は相手自身の内容だけ」と明示した | 21 / 21 |

- **positive の追加は効き、negative（除外）の追加は壊す。**「好み・習慣も残す」で 0/5 → 5/5、「予定も残す」で 0/3 → 3/3 になった一方、除外の例外を広げた変更は 24/33 → 21/33 に落ち、過剰抽出（人格変更の要求を記憶にする）まで起きた。
- **冗談と人格変更の要求は、規則を書く前から候補にならなかった。**規則を足すと他の抽出が減ったので、足していない。
- 関心・関係性の抽出でも同じことが起きた。除外を6つ並べた最初の指示文は全ケース0件で、「出すもの」を例つきで先に書いて動いた。

そのため、記憶の抽出と関心・関係性の抽出は**別の呼び出し**にしている。役割を
分ければ、片方の調整がもう片方を壊さない。記憶の抽出自体も「拾う → 選ぶ」に
分けた。ただし**役割を分けても、選ぶ側に除外を書くと positive が消える**という
同じ形は再現した（受け止めが 3/3 → 0/3）。

### 振り返りにかかる時間

会話の終了でモデルを3回呼ぶようになった。

| 段階 | 平均 |
| --- | ---: |
| 拾う | 3.9 秒 |

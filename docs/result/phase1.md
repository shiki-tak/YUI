### 推論モデル

設計書の初期候補は Qwen3 8B だったが、実測に基づき **qwen3.5:9b（思考出力なし）** を採用した。

記憶に答えがある質問（「私の趣味が何なのか知っていますか？」）を同じプロンプトで繰り返し投げた結果：

| モデル | 記憶を使って答えた | 応答時間 |
| --- | --- | --- |
| gemma4 | 20回中10回（多くは否定してから覆す） | 8〜16秒 |
| qwen3.5:9b（思考あり） | 8回中8回 | 平均106秒 |
| qwen3.5:9b（思考なし） | 5回中5回 | 平均1.7秒 |

gemma4 では記憶を渡していても半数は「知らない」と答えた。プロンプト側の調整（相手と記憶の結びつけの明示、否定側の指示の削除）でははっきりした改善が出ず、モデルの差だった。

思考出力は切っている。切っても記憶を使う正確さは変わらず、応答時間だけが約60分の1になった。`YUI_OLLAMA_THINK` で切り替えられる。

## 設計上の約束と、実装での対応

設計書が「混同しない」としている区別を、構造として持たせている。

| 設計の区別 | 実装 |
| --- | --- |
| 会話履歴と長期記憶を分ける | `messages` と `memories` を別テーブルにし、会話ログをそのまま昇格させない |
| 事実と推測を分ける | `memories.certainty`（fact / inference）。プロンプトでも節を分けて示す |
| 記憶に根拠を残して訂正可能にする | `source_message_id` で根拠の発言を指し、画面から本文を開ける。`memory_revisions` に更新前後を残す |
| 生成しただけの文章と、実際に届いた文章を混同しない | `messages.delivery_state`（フェーズ2で音声再生の状態へ拡張） |
| 人物は表示名でなく入力元の識別子で同定 | `speakers (source, external_id)` に一意制約 |
| 非公開の記憶を配信に混入させない | `visibility`（private / public）と `visible_to_speaker_id`（誰との会話で参照してよいか）を別の軸として持つ |
| 記憶の更新候補は開発者が確認してから採用 | `memory_candidates` に pending / accepted / rejected を持たせ、画面で判断 |

`visible_to_speaker_id` は、レビューで「相手に紐づかない非公開記憶が別の相手へ渡る」と指摘されて追加した。「誰についての記憶か」と「誰が参照してよいか」は別の軸だという整理である。

## 記憶検索の方式

形態素解析は入れず、「相手・時刻・キーワード」で検索する。設計書の「初期の記憶検索は相手・時刻・キーワードで始め、必要になった段階で意味検索を追加する」に沿っている。

- **相手**：その相手についての記憶と、相手に紐づかない自分の経験を対象にする。
- **参照範囲**：ローカルでは公開記憶・相手を限定しない記憶・この相手に許可された記憶。配信では公開記憶のみ。
- **キーワード**：英数字語と日本語の2文字ぶんの並びで重なりを数える。ひらがなだけの並びは助詞の切れ端になりやすいため重みを下げる。記憶の種別名（「約束」など）も検索対象に含める。
- **時刻**：新しい記憶をわずかに優先する減衰のみ。
- **約束**：語が一致しなくても直近のものを落とさない。忘れたことに気づけないため。

検索結果には一致の理由と点数を付けて返し、画面で確認できる。

## 並行処理の扱い

SQLite は書き込みロックを1つしか持てないため、生成の応答を待つ間はトランザクションを閉じる。そのうえで、会話ごとのプロセス内ロック（`turn_lock.py`）で順序を守る。

- 生成中でも、他の会話や記憶の訂正は止まらない。
- 同じ会話への同時送信は直列化され、「質問A → 返答A → 質問B → 返答B」の順になる。
- 会話の終了（振り返り）も同じロックを使い、状態の判定はロックの内側で行う。
- 振り返りは「処理中」と「完了」を分け、中断やプロセス停止で開始だけが残った場合は一定時間後にやり直せる。

MVPは単一プロセスのためプロセス内のロックで足りる。複数プロセスに分ける段階では置き換えが必要（[ISSUE-007](../issues/issues.md)）。

## 振り返り（記憶候補の抽出）

会話終了時に、会話ログへ発言IDを付けてLLMへ渡し、候補ごとに根拠の発言を選ばせる。

- 出力を候補として読み取れない場合は失敗として扱い、「残す価値が無かった（空の配列）」と区別する。
- 要素が1件でも読み取れなければ全体を失敗とし、有効だった候補も保存しない。落とした候補は「記憶になり損ねた経験」であり、静かに捨てると失われたことに気づけないため。
- 失敗しても会話は終了状態にならず、続きを話すことも振り返りをやり直すこともできる。
- 存在しない発言IDを返された場合は「根拠未確認」として残し、無関係な発言へ付け替えない。

厳格化の副作用は事前に計測した。実際の振り返りプロンプトを qwen3.5:9b へ36回投げ、要素38個すべてが検証を通過した。

## 記録しているデータ

設計書「この段階から保存する」項目はすべて保存している。

| データ | テーブル |
| --- | --- |
| 入力・返答・生成の状態 | `messages` |
| 参照した記憶・モデルの版・生成設定・応答時間・トークン数・実際のプロンプト | `run_records` |
| 修正した理想の返答 | `ideal_responses` |
| 長期記憶と変更履歴 | `memories` / `memory_revisions` |
| 記憶の更新候補 | `memory_candidates` |
| 相手 | `speakers` |

## 検証

# フェーズ4：経験に基づく自発性 実装記録

対象：[docs/design/ai_vtuber_development_phases.md](../design/ai_vtuber_development_phases.md) の
「6. フェーズ4：経験に基づく自発性」

**状態：測定完了（2026-09-09）。完了の判断はレビューに委ねる。**

設計書の「最初の小さな実験」は、実モデルで端から端まで成立した。ただし安定
しない。**自動採用は `promise` だけを有効にした。** 一度は `goal` も有効にしたが、
第1回レビューで採用された48件を読み直し、1つの会話から2件以上を採用した回が
33回中13回あったため外した（[phase4_status.md](phase4_status.md)）。

一度は「仕組みを作って測ったから完了」と整理したが、それは都合の良い線引き
だった。実装内容9は「自動採用へ移す」で、**1種類も移していないなら移して
いない**。そこから、塞いでいた2つの抽出の欠陥を直した。

その実装に都合の良い測り方になる。

## 測り方

判定は3つに分ける。**モックでの成功と、実モデルでの振る舞いを混同しない**ため。

- 制御テスト：pytest（隔離DBとモック）。実装の振る舞いを固定する。
- 実モデル評価：`python -m app.evaluation.run`（qwen3.5:9b、人格 `2026-09-07.1`、各3回）。
- 人手：レポートの「人が見る点」を読んで判断する。

**合計点を結論に使わない**（[ISSUE-032](../issues/issues.md#issue-032)）。PR10 で、
**同一コードの2回実行で 43 シナリオ中 16 が動く**ことを実測した。`3/3 → 1/3` の
ように3試行のうち2回分動くので、数点の差は揺れと区別できない。

代わりに揺れないものを見る。

1. **自動採用が実際に入れたものの中身。** モデルの出力そのもので、合否の判定を
   経由しない。設計書「自動化の合否を単なる採用件数で測りません」に対応する。
2. 落ちた判定の**種類ごとの件数**。シナリオ単位より揺れが薄まる。
3. 機械で**一意に決まる**判定（基準日など）。

## 自動採用（実装内容9）

### 塞いでいたもの

最初の測定（全種類を有効）で、**開発者の確認を経ずに入った記憶114件のうち、
58件が誤った入手経路**、**10件が人格変更の要求から**作られていた。この状態では
どの種類も有効にできない。原因は2つあり、どちらも直した。

**1. 同じ軸を2回訊いていた**（[ISSUE-023](../issues/issues.md#issue-023)）。
指示文の定義は `provenance`「firsthand は、話している相手**自身**についての
内容だけ」、`about_partner`「話している相手自身についての内容のときだけ true」
で、同じことを別の言葉で訊いている。**食い違えば、必ずどちらかが誤りになる。**

`provenance` を出力から外し、`about_partner` から導出した。

| 期待 | 変更前 | 変更後 |
| --- | --- | --- |
| 「弟は辛いものが苦手」→ 伝聞 | 3/4 | 3/4 |
| 「仕事が立て込んでいる」→ 本人 | 4/4 | 4/4 |
| **「友人の結婚式で名古屋に行く」→ 本人** | **0/4** | **4/4** |

誤りの正体は「**文中に他人が出てくると、本人の話でも伝聞にする**」だった。
他人が出てこない文は変更前から 4/4 正しい。

`impression` は YUI 自身の受け止め方なので `about_partner` が false になり、
導出が伝聞へ倒れる。**自分が感じたことを人づてに聞いたことにはならない**ので、
種類から導出するようにした（0/8 の誤りが解消）。

**2. 人格変更の要求が候補になる**（[ISSUE-033](../issues/issues.md#issue-033)）。
抽出の指示文に**人格に関する規則が1つも無かった**。追加して 0/3 → 2/3。
あわせて、採用側に安全弁を置いた（人格・口調に関わる語を含む候補は、種類が
有効でも自動採用しない）。**候補としては残る**ので開発者は採用できる。

### どの種類を有効にできるか

全種類を有効にして測り、**入った中身を読んで**決めた（`20260909T121009`、
記憶90件）。

| 種類 | 全体 | 残すべきでない筋書き | 誤った入手経路 | 判断 |
| --- | ---: | ---: | ---: | --- |
| **`promise`** | 15 | **0** | **0** | **有効** |
| `goal` | 47 | 0 | — | 一度は有効 → **レビュー後に外した**（重複・時期違いが 33回中13回。[phase4_status.md](phase4_status.md)） |
| `relationship` | 6 | 0 | — | 観測が薄い |
| `impression` | 8 | 1 | 0 | 手動 |
| `about_person` | 23 | 1 | 2 | 手動 |
| `experience` | 44 | 1 | 4 | 手動 |
| `interest` | 30 | **4** | — | 手動 |
| `fact` | 0 | — | — | 観測なし |

「残すべきでない筋書き」は、冗談・雑談・人格変更の要求から候補を作った回。

**数字だけ見ていたら間違えた。** `impression` は誤った入手経路が 0/8 で、数字上は
最も綺麗である。中身を読むと、冗談の会話から「開発者の表情が立派だったと評価
した」を採用していた。**YUI は表情を見られない**——架空の観察である。設計書
「自動化の合否を単なる採用件数で測りません」が、そのまま当てはまった。

`interest` は冗談から「10 億円当てた時の本当の感情を知りたい」を採用しており、
最も明確に不適格だった。

### 回ごとに揺れたシナリオ（参考）

`joke-is-not-kept` は、同日の4回の実行で 1/3・2/3・0/3・2/3 と動いた
（ログ `20260909T111059`、`121009`、`133300`、`143353`）。同一条件でも
3試行のうち2回分動く例で、[ISSUE-032](../issues/issues.md#issue-032) の実例である。

### 有効にした状態で測り直した

出荷時の設定で流すと、自動採用されたのは **目標48件・約束16件**（有効にした
種類だけ。他の種類の採用はシナリオの `accept` 手順による手動採用である）。

**残すべきでない筋書きでの自動採用は1件**：雑談から「「青い空」の実際の色を
聞く」という目標。直前の実行では0件だったので、2回で 1/95 である。**不要な
質問が1件生まれる**という害で、期限切れ（`goal_expiry_days`）で消え、
`does-not-pile-up-questions` は 3/3 のまま。

`promise` の入手経路の誤りが1件出た。「YUI は開発者の写真を見たいと言って
いる」——YUI 自身のことなので `about_partner` が false になり伝聞へ倒れる。
`impression` で直したのと同じ構造だが、**種類では判別できない**（YUI について
語る `promise` もありうる）ので残課題とする。

## 測って分かったこと

### 1. 判定は、実装より壊れやすい

PR10 で判定を作り直したところ、**測るたびに判定か実装の穴が1つずつ出た**。

| 見つかったもの | どちらの穴か |
| --- | --- |
| 「日本語のまま」の判定に日本語の漢字が混ざり、正しい返答を5シナリオで落とした | 判定 |
| 「么」「儿」に日本語の用例があり、麻雀・部首の説明を落とす | 判定 |
| 仮名が無いだけで「東京都千代田区」を落とす | 判定 |
| 宣言した数値の期待が、判定しない手順にも書けた（検査0件で合格） | 判定 |
| 本文と日付が別の目標で満たされても通る | 判定 |
| 日付の起点がシナリオ最初の発言に固定されていた | 判定 |
| 通しのシナリオが質問で終わり、完了処理を壊しても通った | 判定 |
| 基準日の「予定の翌日」の +1 だけを落としていた | 実装 |
| 鳴らずに止めた質問が達成の根拠になっていた | 実装 |

**数字が下がって見えるだけの誤りは、「モデルの品質問題」として片付けてしまえる。**
落ちた回の返答を人が読むまで気づかなかった。

### 2. 3試行では、指示文の効果を揺れと区別できない

同一コードの2回実行で、43 シナリオ中 16 が動いた。うち11は揺れである。
[ISSUE-032](../issues/issues.md#issue-032) に記録した。

実際、[ISSUE-031](../issues/issues.md#issue-031) に対する指示文の変更（「会話が
まだ始まっていないことは待つ理由にならない」）を測ったが、**目標があるのに
待機した割合は 11/80 → 3/25 で変更前の幅の中**だった。決め手は割合ではなく
**理由の文**で、変更後も

> 会話がまだ始まっていないため、挨拶や雑談で流れを作る必要がある。

が3回とも出た。指示文が名指しで禁じた理由がそのまま返ってきている。効果を
示せない追加は残さない方針（[ISSUE-021](../issues/issues.md#issue-021)）に従って
戻した。

### 3. 足し算はモデルにやらせない

基準日の誤り（[ISSUE-028](../issues/issues.md#issue-028)）は、鋭い判定で測り直すと
**「予定の翌日にする」の +1 だけ**を落としていた。曜日から日付を出すところまでは
当たっている。足し算をモデルからコードへ移したら（`event_date` を答えさせて
`_parse_event_date` が +1 する）、**1日ずれは修正後の12試行で0回**になった。

### 4. 同じことを2回訊くと、必ずどちらかが誤る

入手経路の誤り（114件中58件）の原因は、モデルの能力ではなく**訊き方**だった。
`provenance` と `about_partner` が、指示文の定義上まったく同じことを訊いていた。
訊くのを1つにしてコードで導出したら 0/4 → 4/4 になった。

PR10 の「足し算はモデルにやらせない」と同じで、**導出できるものを訊かない**。

### 5. 数字が綺麗な種類が、安全な種類とは限らない

`impression` は誤った入手経路が 0/8 で、種類別では最良だった。中身を読むと、
冗談から「開発者の表情が立派だったと評価した」を採用していた。YUI は表情を
見られない。**採用件数でも誤り率でもなく、何が入ったかを読む**しかなかった。

### 6. 測る道具の穴は、集計にも開く

PR11 で評価に自動採用を通すとき、**評価は振り返りの保存を別に持っていた**。
そのままでは自動採用を有効にしても一度も通らない測定になる。本番と評価の
両方が同じ関数を呼ぶ形にしてテストで固定した。

PR12 の集計スクリプトでも同じ形を踏んだ。**人手のみのシナリオを合計に混ぜて**
レポートと数字が合わなくなり、それを実行結果から復元しようとして失敗した
（言語の判定はすべてのターンに付くので、実行された判定は必ず1つ以上ある）。
分類は宣言側にしか無い。

さらにもう一度踏んだ。レポートは状態と目標を個別に「自動採用」と出すのに、
**記憶だけ「採用した記憶 N 件」という件数**だった。区別が無いので、集計が
自動採用と手動採用を混ぜ、**有効にしていない種類が「採用された」と出た**。
「未確認」に書いていた穴が、そのまま自分の分析を狂わせた。記憶も1件ずつ
「自動採用／採用」を出すように直して測り直した。

## 未確認・残っていること

**フェーズ4で既成事実にしない。**

- **完了条件5に対応する評価シナリオが無い。** `action_records` と
  `goal_revisions`、PR11 の一括取り消しは pytest で固定しているが、**通し評価では
  一度も測っていない**。他の条件と同じ重さで扱えない。
- **実プロセスでの再起動を確認していない。** 評価の `restart` は接続と担当の
  作り直しで、プロセスは落としていない（[ISSUE-025](../issues/issues.md#issue-025)）。
- **実 VOICEVOX・実ブラウザでの通し確認をしていない。** 再生の状態は API を
  直接叩いて測った。画面はモック API での単体テストのみ。
- **開発用DB（`backend/data/yui.db`）にマイグレーションを適用していない。**
- **qwen3.5:9b と人格 `2026-09-07.1` 以外で評価していない。** 別のモデル・別の
  人格版で同じ結果になるかは分からない。
- **人が読んで判断する5シナリオを読んでいない。** 口調・着眼点・迎合していないかは
  自動判定の対象外で、通ったとも通らなかったとも言えない。
- **自動採用を有効にした長時間運用を見ていない。** 採用が積み上がったときの
  挙動は未確認。目標が積み上がる影響（不要な質問の蓄積）は、1回の会話の中では
  `does-not-pile-up-questions` 3/3 で見ているが、**日をまたいで溜まる形は
  測っていない**。
- **`relationship` と `fact` は根拠を持たずに手動のままにした。** `relationship`
  は観測6件で薄く、`fact` は観測が無い。**根拠が無いという意味であり、危険だと
  分かったという意味ではない。**
- **「差が無い」ことは証明していない。** 自動採用の有無で合計が観測範囲に
  収まったことは、影響がゼロである証明ではない。

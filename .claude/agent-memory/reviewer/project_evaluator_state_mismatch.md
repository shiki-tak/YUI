**Why:** 評価器は PR の受け入れ条件（§7 のシナリオを 3 回）そのもの。評価器側の誤判定は
「実装が悪い」と読まれて無駄な修正を誘発するか、逆に人手判定で片付けられて欠陥を隠す。
pytest は ID や返答を直接埋め込むため、この種の不一致は pytest では見つからない。
記録の数字は `report.json` に設定値（`conversation_state_llm` 等）が入っておらず、記録にログ ID も無いと後から検証できない。

**How to apply:** 評価器の期待値・チェック・手順を変える diff では、
- 実装がどの時点（生成前／後）・どの話者向けの状態で判定したかを確認し、評価器は実装の記録
  （`RunRecord.options`）を再利用できるならそれを使う
- 複数話者のシナリオは、期待する状態の target が say の話者と一致するかを見る
- 変えた手順（`correct_memory` 等）を使う**同梱 TOML を `load_scenarios` で読み**、issue や記録に書かれた
  抽出結果を FakeLLM で再現して `run_scenarios` に流す。pytest 内の自作シナリオだけでは同梱側の破れを見逃す
- 記録（`docs/result/*.md`）の合否数は `logs/evals/<id>/report.md` の見出し（「自動判定を通った試行」）で
  突き合わせる。**`report.json` の `passed`/`total` を足すと数字が変わる**——json には `human_only` が
  無く、人手のみのシナリオが `1/1` として混ざる（165201 は md 38/52・json 44/58）。json を使うのは
  `failed_to_run` の内訳や失敗メッセージを追うとき。
  どのログか特定できない数字（解釈あり／なし、待ち時間表）は根拠不足として指摘する。
  「最大◯秒」「一度も超えない」のような**極値・全称の主張**は、根拠ログ1本ではなく
  記録が言及している全実行を見る（別の回の最大値の方が大きいことがある）。
  記録が「ログに〜が残る」と書く設定値・キーは、そのログの json を `grep` して実在を確かめる（修正前の実行を引いていることがある）。
  記録が引くログの時刻が diff の変更より前でないか（`logs/evals` の新しい ID が記録に出てこないか）も見る
- 測り直した数字は、**同じ実行から引いている表・設定値・コメントを全部**洗う
  （`docs/result/` の別の節、`docs/plan/` の設定表、`app/config.py` のコメント）。
  更新されるのは本文だけで、表と設定値の根拠が前の実行のまま残る
- `logs/` は `.gitignore` されている。記録がログ ID だけを根拠に挙げている数字は、
  他の環境からは検証できない。成果物を足す修正では、数字そのものを記録に写しているかを見る
- 評価器に**新しい失敗の種類**（シナリオ記述の不備を実行時に捕まえる等）を足す diff は、
  既存の集計指標（`failed_to_run`・`passed`・`human_only`）の意味が変わっていないかを見る。
  モデルの失敗とシナリオの書き間違いが同じ数字に混ざると、記録の「クラッシュ0件」が検証できなくなる
- 新しいシナリオ項目（`accept_limit` 等）は、`StepSpec` のフィールド定義のコメントが
  最終仕様と一致しているかを見る。設計を途中で変えると、ここだけ旧仕様の説明が残る
- 記録が「〜は絞られない／毎ターン増える／上限が無い」と**実装の機序**を説明する文を
  書いていたら、その語を実装に `grep` する（`*_LIMIT` 定数・スライス・`[-N:]`）。
  数字と違って一見検証不要に見えるが、過去のレビューで入れた上限と正反対のことが書かれる
- 数字表を更新したら、**同じ語で書かれた他節**（「直近の回帰」「既知の失敗」「制御テスト」）を
  同じ文書内で grep する。表だけ新しくなり、本文と一覧が前の版のまま残って同一文書内で矛盾する。
  issue を「完了」に移す修正では、設計書 §8.1 の既知の失敗一覧に残っていないかも見る
- 記録・README・設計書が「〜できる」と書く機能は、**出荷時の既定値で実際に起きるか**を
  `Settings()` のまま1本会話を流して確かめる。v0.2 は解釈が既定無効で、
  `request`／`correction`／`discrepancy` は規則では一切作られない。
  6回目（実装の機序）・7回目（極値・全称）・9回目（既定無効の機能）と、
  **記録が実装の到達範囲を実際より広く書く**形は繰り返し出ている
- 判断点・完了の記録が「0件」「満たす」と書く条件は、対応する同梱 TOML の `description`／`human_check` に
  「人手で読む」が無いか、`report.json` の `human_check` が空でないかを見る。機械判定が○でも
  返答本文に「？」があれば `detect_question` に通して、途中の文の質問を拾えているか確かめる
- 「曖昧さ・非決定性を塞いだ」と書く修正は、塞いだのが**検出**なのか**原因**なのかを分ける。
  候補の選び方が LLM の出力順に残っていれば、検出器が無言になるぶん前より悪い

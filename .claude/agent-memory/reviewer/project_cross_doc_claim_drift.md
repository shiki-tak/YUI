docs を直す diff で、**同じ主張を書いた別の場所が更新されずに矛盾する**形が v0.2 で 5 回以上出ている（2026-09-15 時点）。
- PR5：`docs/result` 本文を再測定に更新、`docs/plan/v0.2.md` の設定表と `config.py` のコメントは旧値
- PR5：数字表を更新、同じ設計書の §8.1「直近の回帰」と既知の失敗一覧は前の版
- PR5：README の機能箇条書きが、既定で無効な経路を実装済みとして書く
- 2026-09-15（構成図の修正）：`architecture.mmd` から WebSocket を消し ISSUE-040 で「図を実装へ合わせた」と書いたが、
  設計書 §3.2 の技術表（「HTTP・WebSocket」）と §3 の図は未修正。
  同じ diff で ISSUE-040 が「v0.6 は push が要る」と書いたが、設計書 §8.5/§8.6 は
  「セッション開始の API」「K ターン後の再試行」「話題の区切りの検出はしない」で、どれもクライアント発の要求で足りる
- 同 diff：issues.md 前文が「6 件はいったんクローズにしていた」と書いたが、ISSUE-030 は HEAD で「未着手」のまま開いていた

**Why:** README は設計書を唯一の設計の出所として指し、設計書は版ごとの表・技術表・図・既知の制限一覧に
同じ事実を複数回書いている。1 か所だけ直すと、残りが「実装より広い」または「実装より古い」主張として残り、
次の版の計画がそれを根拠に組まれる。

**How to apply:** docs 変更の diff では、変えた主張のキーワード（技術名・版番号・状態名・「実装済み」等）を
`docs/ README.md backend/app/config.py` に grep し、同じ主張が別の場所に残っていないかを列挙する。
issue の「いつ扱うか」が版を指すときは、設計書のその版の表（追加する仕組み・対象外）を読んで、
本当にその版で必要になるかを確かめる。issue を削除・状態変更する diff では、HEAD の一覧表の状態欄と
本文の「状態：」行を見て、前文の要約（「クローズだった」等）が全件に当てはまるかを見る。
